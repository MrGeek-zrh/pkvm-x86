# 分析：pkvm-v6.18 是否支持将设备透传给 pVM（protected VM）

## 结论（基于源码证据）
当前 `pkvm-v6.18`（x86 pKVM / `CONFIG_PKVM_INTEL`）**不支持**把真实硬件设备（典型是 PCIe 设备，经 VFIO/直通）“透传/直通”给 pVM 使用。

更具体地说：pVM 的二阶段映射（stage-2）路径在“把 host 物理地址映射进 pVM GPA”时 **强制要求 HPA 属于普通 DRAM 内存范围**，从而 **无法映射设备 MMIO（例如 PCI BAR）到 pVM**；同时 pVM 也不支持传统的 MMIO emulation 退回到 host/userspace 的路径。结合 pKVM ABI 中缺失 IOMMU/设备隔离相关接口，可判定“设备透传给 pVM”在该版本中没有实现。

> 说明：这里“支持”按内核侧能力/代码路径可实现为准，不讨论“改一堆代码/补 IOMMU/补 hypercall 之后可能支持”。

---

## 设备透传的最小需求（本文使用的判定口径）
要让 pVM 直接使用真实 PCIe 设备（VFIO passthrough 常见做法），至少需要：

1. **pVM 能访问设备寄存器**：需要把设备 BAR（MMIO 物理地址区间）映射到 pVM 的 GPA（或通过某种受支持的机制进行寄存器访问）。
2. **设备能 DMA 到 pVM 内存**：需要可信实体配置/约束 IOMMU，确保 DMA 只到允许的 guest 内存（在 pKVM 威胁模型下 host/VMM 不可信时尤其关键）。

本文用第 1 点作为“是否能直通”的硬门槛（如果连 BAR 都映射不进去，就谈不上直通设备）。

---

## 源码证据 1：pVM 的 stage-2 映射只允许映射“内存范围”，拒绝 MMIO
调用链（每层缩进 4 个空格表示“被调用”）：

```
pkvm_page_fault(vcpu, fault)                               // arch/x86/kvm/mmu/mmu.c
    pkvm_hypercall(vm_mmu_map, ...)                         // arch/x86/kvm/mmu/mmu.c
        pkvm_vm_mmu_map(gpa, hpa, size, writable)           // arch/x86/kvm/pkvm/pkvm.c
            pkvm_host_donate_guest(vcpu, gpa, hpa, size)    // arch/x86/kvm/pkvm/mmu.c
                check_host_mem_pgstate(hpa, size, ...)      // arch/x86/kvm/pkvm/mmu.c
                    is_memory_range(hpa, size)              // arch/x86/kvm/pkvm/memory.h
                        pkvm_find_addr_range(hpa, range)    // arch/x86/kvm/pkvm/memory.c
```
### 1.1 `check_host_mem_pgstate()`：非 DRAM 内存范围直接 `-EINVAL`
文件：`arch/x86/kvm/pkvm/mmu.c`

调用关系（每层缩进 4 个空格表示“被调用”）：

```
check_host_mem_pgstate(phys, size, pgstate)     // arch/x86/kvm/pkvm/mmu.c
    is_memory_range(phys, size)                 // arch/x86/kvm/pkvm/memory.h
        pkvm_find_addr_range(phys, range)       // arch/x86/kvm/pkvm/memory.c
```

并且 `check_host_mem_pgstate()` 内部的关键判断是：如果 `is_memory_range()` 为 false，则直接 `return -EINVAL`（拒绝该物理区间）。


这里 `is_memory_range()` 的语义是“该物理区间是否在 e820/内存 range 里”（见 `arch/x86/kvm/pkvm/memory.h` 的 `is_memory_range()` 实现依赖 `pkvm_find_addr_range()`）。

### 1.2 `pkvm_host_donate_guest()`：pVM 映射时必须通过 `check_host_mem_pgstate()`
文件：`arch/x86/kvm/pkvm/mmu.c`

调用关系：

```
pkvm_host_donate_guest(vcpu, gpa, hpa, size)                // arch/x86/kvm/pkvm/mmu.c
    check_host_mem_pgstate(hpa, size, PKVM_PAGE_OWNED)       // arch/x86/kvm/pkvm/mmu.c
```


`pkvm_host_donate_guest()` 的注释明确写的是“Donate memory pages from host to guest”，并在逻辑上把 host 页 ownership 交给 guest。
这条路径天然只适用于 **RAM 页**，而不是 MMIO 这种“非 page-managed 的 I/O 物理地址”。

### 1.3 `pkvm_vm_mmu_map()`：对 pVM 使用 donate 路径
文件：`arch/x86/kvm/pkvm/pkvm.c`

调用关系：

```
pkvm_vm_mmu_map(gpa, hpa, size, writable)                   // arch/x86/kvm/pkvm/pkvm.c
    if pkvm_is_protected_vcpu(vcpu)
        pkvm_host_donate_guest(vcpu, gpa, hpa, size)         // arch/x86/kvm/pkvm/mmu.c
    else
        pkvm_host_share_guest(...)
```


即：一旦是 pVM（protected vCPU），stage-2 map 走 `pkvm_host_donate_guest()`。

### 1.4 `pkvm_page_fault()`：KVM 的缺页映射最终会触发上述 `vm_mmu_map`
文件：`arch/x86/kvm/mmu/mmu.c`

调用关系：

```
pkvm_page_fault(vcpu, fault)                               // arch/x86/kvm/mmu/mmu.c
    pkvm_hypercall(vm_mmu_map, base_gpa, host_hpa, ...)       // arch/x86/kvm/mmu/mmu.c
```


**推论（可落到代码）：**
- 若尝试把设备 BAR 之类的 MMIO 区间作为 memslot backing（例如 userspace mmap VFIO region，然后 `KVM_SET_USER_MEMORY_REGION` 映射到 guest GPA），`fault->pfn` 对应的 HPA 将落在 **非 DRAM** 的物理地址段。
- 随后 `pkvm_host_donate_guest()` 会因为 `check_host_mem_pgstate()` 的 `!is_memory_range()` 而返回 `-EINVAL`。

因此 **pVM 无法把设备 MMIO（PCI BAR）映射进来**，设备寄存器都不可达，设备透传在内核侧直接被卡住。

## 源码证据 2：pVM 不支持传统 MMIO emulation 兜底路径
文件：`arch/x86/kvm/mmu/mmu.c`

调用关系：

```
pkvm_page_fault(vcpu, fault)                               // arch/x86/kvm/mmu/mmu.c
    if pkvm_is_protected_vcpu(vcpu) && r == RET_PF_EMULATE
        return -EFAULT                                       // pVM 不走 MMIO emulation
```


这意味着当缺页路径判断需要走 MMIO emulation（典型是访问未被 backing 的 MMIO GPA）时，pVM 直接失败，不会像普通 VM 一样通过 `KVM_EXIT_MMIO` 等机制让 host/userspace 去模拟。

该限制进一步说明：就算不能直通设备，也不能指望“传统 userspace 设备模型”通过 MMIO trap/emulate 来工作。

---

## 源码证据 3：pKVM hypercall ABI 未包含 IOMMU/设备直通相关接口
文件：`arch/x86/include/asm/pkvm_hypercalls.h`

该文件列出的 hypercall 主要覆盖：VM/VCpu 生命周期、寄存器同步、TLB 刷新、以及 `vm_mmu_map/unmap/age`。
**没有**任何用于：
- 配置 VT-d/IOMMU（domain、PASID、page table 等）
- 把某个物理设备隔离/绑定给某个 pVM
- 建立 “device DMA → guest private memory” 的可信映射

在“host/VMM 不可信”的 pKVM 威胁模型下，如果要安全支持设备透传，通常需要 hypervisor 侧控制 IOMMU；但本版本接口层面就缺失。

（相关威胁模型描述可见 `arch/x86/kvm/vmx/pkvm_init.c` 中关于“host/VMM 在用户态且不可信”的注释。）

---

## 接口侧补充：该树确实引入了 pVM 类型，但未体现设备直通能力
文件：`arch/x86/include/uapi/asm/kvm.h`

- 定义了 `KVM_X86_PKVM_PROTECTED_VM`（该树临时取值 28，注释说明为避免与 upstream 冲突）。
- 定义了 `struct kvm_protected_vm_info` 等与 protected VM 相关的能力位。

这表明该源码树的目标是“能创建/运行 protected VM”，但结合前述映射限制，可以看出 I/O/设备直通并未实现到可用状态。

---

## commit log 侧证（不是决定性证据，但可辅助判断范围）
在该分支 pKVM 相关目录的提交历史中，未见与 `VFIO/IOMMU/PCI passthrough` 直接相关的提交描述：

```bash
git log --oneline -- arch/x86/kvm/pkvm arch/x86/kvm/vmx/pkvm_* arch/x86/include/asm/pkvm_hypercalls.h | rg -n "vfio|iommu|passthrough|pci|device"
```

结合源码结构（pKVM 代码中几乎不出现 `iommu/vtd/dmar` 相关关键字），更符合“当前阶段聚焦内存/CPU state 保护与启动链路”，而非“设备直通/IOMMU 隔离”。

---

## 小结
- **硬证据**：pVM 的 `vm_mmu_map` → `pkvm_host_donate_guest` 链路要求 `is_memory_range()`，直接阻断把设备 MMIO（PCI BAR）映射进 pVM 的可能性。
- **配套证据**：pVM 不支持传统 MMIO emulation；pKVM hypercall ABI 不包含 IOMMU/设备隔离能力。

因此，在 `pkvm-v6.18` 这份源码中，“将设备透传给 pVM”不成立。
