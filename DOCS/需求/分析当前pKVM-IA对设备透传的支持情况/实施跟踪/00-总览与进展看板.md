# pVM 设备透传实施总览与进展看板

## 当前目标

在不破坏 pVM `donate` 安全模型的前提下，把当前 `pKVM-IA` 中已经存在但未补全的 pVM 设备透传骨架真正落地，最终实现：

- pVM 可以 attach VFIO 设备。
- guest 页面 donate 给 pVM 后，可同步进入设备 DMA 可见视图。
- teardown 时不会出现设备仍可 DMA 到已归还 host 页的生命周期错误。

## 当前结论

- 已确认主线方案应收敛到方案 B: `donate + pVM DMA mirror pgtable`。
- 已确认源码已经具备核心骨架：`pgstate_pgt -> ptdev->pgt -> IOMMU SLPTR`。
- 已确认当前 panic 的直接根因是旧 host shadow IOMMU spgt 残留的数据页 refcount 阻塞 donate。
- 已确认 teardown 还存在一个文档之外的硬约束：当前 `pkvm_detach_ptdev()` 是“切回 host IOMMU 视图”，不是“真正 quiesce 设备 DMA”。
- 已完成 T1 首轮运行验证：`NoIommu` 路径下已不再出现 `host_initiate_donation: page refcounted`、`do_donate failed ret=-16`、`pgtable_unmap_leaf` assertion 或 `pkvm: exception`。
- 当前最新阻塞已完成更高置信度归因：官方 issue `#46` 与本地 guest 源码一致表明，当前分支里的 protected pVM 设备透传本身尚未真正支持。crosvm 的 config/MMIO fallback 只是较早暴露出来的症状，T2/T3 的 DMA mirror 也还不是当前最前置 blocker。
- 已进一步确认真正的主线前置缺口不止是“MMIO 分流”，还包括“透传设备 BAR/MMIO 资源信息如何传给 guest/hyp”这一 contract。当前 host->pKVM 接口只传了 `BDF/PASID`，并没有 BAR/resource 元数据。
- 已开始把协作流程收敛到 GitHub Issue / PR 模式，并将 `pKVM-IA` 纳入当前 superproject 的 submodule 管理，以便把“问题状态”“内核修复 PR”“superproject 集成点”串成闭环。
- 已确认接下来的推进方式应先从上层方案收敛开始，而不是继续下钻到底层 ioctl / hypercall 细节。当前更合适的是先确定“第一阶段到底支持什么、不支持什么、trust boundary 放在哪、先解决哪条访问面”。
- 已确认 ARM64 pKVM/AVF 是当前最值得参考的成熟实现，但参考重点应是“上层模式和 trust boundary”，而不是直接照搬 ARM 的 device-assignment 代码路径。

## 拆分原则

- 先拆“直接阻塞启动”的 correctness 问题，再拆“让功能真正可用”的同步问题。
- 按生命周期边界拆，而不是按文件名拆。
- 每个子任务都必须有明确输入、输出、验收标准和源码锚点。
- 把“问题记录”和“实施任务”分开维护。
- 对大工程先做自顶向下收敛：先定能力边界、trust model、阶段目标，再细化到 UAPI、guest/hyp contract 和具体代码改动。

## 阶段划分

### 阶段 0: 设计收敛

- 完成方案可行性确认。
- 完成任务拆分、依赖关系和验证矩阵。

### 阶段 1: P0 correctness

- 清理旧 shadow spgt 残留 refcount。
- 对 `NoIommu` 主线运行期 `EFAULT` 做阻塞归因。
- 设计 protected pVM guest/hyp 的 passthrough MMIO contract。
- 收敛 `pgstate_pgt` 语义为纯 DMA mirror。
- 在 donate 成功后同步 runtime DMA mirror。
- 在 VM teardown 前 quiesce ptdev DMA。

### 阶段 2: P1 功能补全

- 首次 attach / 热插拔 prepopulate。
- VFIO remove-path、失败回滚、多设备共享场景。

### 阶段 3: 验证与回归

- 端到端启动验证。
- DMA 读写验证。
- teardown 安全性验证。
- 非 pVM / host shadow IOMMU 路径回归验证。

## 推荐推进顺序

1. 先做 T1，解除当前最直接的 donate 阻塞。
2. 再做 B1，先判断 `BOOT-007` 是 T2/T3 缺失的自然后果，还是独立 bug 线。
3. B1 已完成更高置信度归因，当前应先承认“当前分支尚不支持 protected pVM 设备透传”这一 capability gap。
4. B2 仅保留为候选 workaround，用于实验性验证失败点是否还能继续后移。
5. 主线前置任务应切换到 B3，但 B3 的第一步不是直接写接口草案，而是先定“上层方案”：
   - 第一阶段支持范围
   - 明确非目标
   - trust boundary
   - config / BAR / MSI-X / DMA 的阶段性处理策略
6. 只有在上层方案收敛后，B3 才继续下钻 guest/hyp MMIO contract 和设备元数据通道。
7. 只有在 B3 把上层方案和 MMIO contract 都定清楚后，再做 T2/T3/T4 才有意义。

## 当前进展

- 已完成：方案可行性核对、关键源码锚点确认、任务拆分、T1 代码修复、T1 首轮运行验证、GitHub Issue / PR 协作流骨架落地、`pKVM-IA` submodule 接入。
- 已完成：`pkvm-x86` 远端 Project `#3` 和当前 `13` 个 Epic / Task / Bug issues 初始化。
- 当前阻塞：官方结论与源码一致，当前 capability gap 位于 protected pVM guest/hyp 的 MMIO 语义，而不是单纯的 crosvm 路径。
- 当前下一步：先推进 B3 的“上层方案收敛”，先定第一阶段的低复杂度目标，而不是直接实现底层接口。当前倾向的低复杂度上层方案是：
  - 不追求第一阶段就做完整、安全、通用的设备透传框架
  - 第一阶段只支持单设备、静态 attach、`NoIommu`、无 hotplug、无 migration、无 remove-path
  - config space 继续 emulated
  - 普通 BAR MMIO 作为优先打通的访问面
  - MSI-X table / PBA 暂不做直达，继续 emulate 或明确列为非目标
  - authoritative metadata 仍必须最终落在 pKVM/hyp，而不是停在 host KVM
  - 对应上层方案决议文档：`01C-1-B3-1-protected-pVM-设备透传第一阶段上层方案.md`
  - ARM 参考实现可重点借鉴：
    - device metadata / manifest 通道
    - guest MMIO 分类机制
    - pKVM/hyp 持有 authoritative device state
- B3-2 当前已开始收敛第一阶段所需的 x86 `ptdev metadata` 最小结构：
  - hyp 内部保留富 metadata
  - guest 只消费精简 allowlist
  - 对应文档：`01C-2-B3-2-x86-ptdev-metadata-最小结构草案.md`
  - 当前接口方向：
    - userspace -> host KVM 继续沿用 `KVM_ENABLE_CAP(KVM_CAP_X86_PROTECTED_VM)`
    - guest -> pKVM/hyp 新增专用 hypercall 查询 allowlist
  - 当前 ABI 决议：
    - metadata 必须在第一次 `KVM_RUN` 前提交
    - 第一阶段冻结 metadata，不支持运行期修改
    - guest 启动早期查询并缓存 allowlist
    - guest allowlist 只暴露 `DIRECT_BAR` 语义
  - 当前已补齐：
    - 推荐 UAPI 常量名与结构体命名
    - 提交接口与查询接口的错误码
    - 幂等提交语义
