# pVM 设备透传实施总览与进展看板

## 当前目标

在不破坏 pVM `donate` 安全模型的前提下，把当前 `pKVM-IA` 中已经存在但未补全的 pVM 设备透传骨架真正落地，最终实现：

- pVM 可以 attach VFIO 设备。
- guest 页面 donate 给 pVM 后，可同步进入设备 DMA 可见视图。
- teardown 时不会出现设备仍可 DMA 到已归还 host 页的生命周期错误。

## 当前结论

- 已确认主线方案应收敛到方案 B: `donate + pVM DMA mirror pgtable`。
- 已确认源码已经具备核心骨架：`pgstate_pgt -> ptdev->pgt -> IOMMU SLPTR`。
- 已确认当前 panic 的直接根因是旧 host shadow IOMMU spgt 残留的数据页 refcount 阻塞 donate。
- 已确认 teardown 还存在一个文档之外的硬约束：当前 `pkvm_detach_ptdev()` 是“切回 host IOMMU 视图”，不是“真正 quiesce 设备 DMA”。
- 已完成 T1 首轮运行验证：`NoIommu` 路径下已不再出现 `host_initiate_donation: page refcounted`、`do_donate failed ret=-16`、`pgtable_unmap_leaf` assertion 或 `pkvm: exception`。
- 当前最新阻塞已切换为更后面的运行期问题：protected pVM + VFIO(`NoIommu`) 已能走到 guest kernel load，但随后 crosvm 在 vCPU 运行阶段命中 `Bad address (os error 14)`；同时只读 MMIO 映射会打印 `failed to create vm mapping (EINVAL)`，该错误按 crosvm 源码语义是可退回 vm-exit 的非致命路径。

## 拆分原则

- 先拆“直接阻塞启动”的 correctness 问题，再拆“让功能真正可用”的同步问题。
- 按生命周期边界拆，而不是按文件名拆。
- 每个子任务都必须有明确输入、输出、验收标准和源码锚点。
- 把“问题记录”和“实施任务”分开维护。

## 阶段划分

### 阶段 0: 设计收敛

- 完成方案可行性确认。
- 完成任务拆分、依赖关系和验证矩阵。

### 阶段 1: P0 correctness

- 清理旧 shadow spgt 残留 refcount。
- 对 `NoIommu` 主线运行期 `EFAULT` 做阻塞归因。
- 收敛 `pgstate_pgt` 语义为纯 DMA mirror。
- 在 donate 成功后同步 runtime DMA mirror。
- 在 VM teardown 前 quiesce ptdev DMA。

### 阶段 2: P1 功能补全

- 首次 attach / 热插拔 prepopulate。
- VFIO remove-path、失败回滚、多设备共享场景。

### 阶段 3: 验证与回归

- 端到端启动验证。
- DMA 读写验证。
- teardown 安全性验证。
- 非 pVM / host shadow IOMMU 路径回归验证。

## 推荐推进顺序

1. 先做 T1，解除当前最直接的 donate 阻塞。
2. 再做 B1，先判断 `BOOT-007` 是 T2/T3 缺失的自然后果，还是独立 bug 线。
3. 如果 B1 归因到现有主线，再做 T2，避免 `pgstate_pgt` 和 guest mmu 在 teardown 阶段双重承担 ownership 回收。
4. 接着做 T3，把“attach 只是切表”推进成“运行中 DMA 真正可用”。
5. 然后做 T4，补齐生命周期正确性，否则即使能启动也不安全。
6. 最后做 T5、T6，补齐 hotplug、remove-path 和异常回滚。
