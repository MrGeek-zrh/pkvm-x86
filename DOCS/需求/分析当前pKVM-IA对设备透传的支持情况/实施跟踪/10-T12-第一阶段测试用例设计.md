# T12 第一阶段测试用例设计

## 目的

本文件把 `T12 / B5-3` 第一阶段代码实现拆成可执行的测试用例，重点验证 protected pVM 设备 MMIO donate 的核心不变量，而不是泛化地做“能启动就算通过”。

当前目标是验证 `pKVM-IA` 分支 `codex/t12-mmio-donate-phase1` 上已经落地的第一阶段实现：Host BAR revoke、Host EPT annotated owner、Host fault deny-remap、DMA view commit、guest DIRECT_BAR contract publish，以及 detach / teardown restore。

本文件只负责测试设计和执行判据。运行后产生的原始日志、trace summary 和结论记录应落到：

```text
DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/验证记录/
```

## 非目标

- 不主动发起全量 Linux 内核编译。
- 不把所有 case 都强行做成一次命令自动 pass/fail。
- 不默认执行写盘、`mkfs`、设备复位、强杀 VMM、主动 host BAR touch 这类可能影响环境的动作。
- 不用本文件替代 GitHub `Task` / `Bug` issue 状态管理。

## 测试执行模式

### `scripted`

一次命令或一组固定命令即可重复执行，脚本可以自动判定 `PASS / FAIL / INCONCLUSIVE`。

适合：启动、guest 枚举、只读 I/O、日志签名扫描、固定日志存在性检查。

### `agent-runbook`

由 Codex 按 runbook 交互式执行、观察、调整命令、对照源码分析结果，并写入验证记录。这里不是要求用户人工操作；除非涉及物理机重启、BIOS 设置、设备物理复位等外部动作，默认由 Codex 执行。

适合：多终端联动、tracefs/kprobe 观测、A/C/B 顺序判断、host BAR deny 分支观察、teardown 后状态残留分析。

### `fault-injection-required`

现有运行环境没有稳定入口可靠触发，需要额外 debug hook、kprobe/ftrace fault injection、内核临时开关或专用测试补丁。

适合：部分 BAR revoke 失败、`pkvm_iommu_sync()` 失败、restore busy 等异常路径。

## 第一阶段核心不变量

T12 第一阶段 attach 主线固定为：

```text
protected pVM VFIO attach
    -> A: revoke Host BAR visibility
        -> Host EPT leaf becomes annotated invalid
        -> owner_id = OWNER_ID_PTDEV_MMIO
    -> C: commit DMA view
        -> ptdev->pgt = &vm->pgstate_pgt
        -> pkvm_iommu_sync() succeeds
        -> dma_view_ready = true
    -> B: publish guest MMIO contract
        -> guest receives DIRECT_BAR allowlist
        -> guest BAR MMIO can use pkvm_direct_mmio_*()
```

detach / teardown 主线固定为：

```text
protected pVM VFIO detach / teardown
    -> withdraw guest MMIO contract
    -> if DMA view is ready, switch ptdev->pgt back to host EPT
    -> pkvm_iommu_sync() back to host view
    -> restore Host EPT BAR idmap
    -> owner = HOST, assignment_state = DETACHED
    -> touched_bar_mask = 0
```

## 崩溃前日志保全要求

Host 内核可能在风险 case 中直接 panic，因此 runtime case 的日志收集不能只依赖 case 结束后的 `dmesg`。执行 protected VFIO、host BAR touch injection、teardown 竞态等风险动作前，必须先完成以下准备：

```text
prepare run dir
    -> status.json = RUNNING
    -> metadata.json 写入 case/BDF/时间
    -> logs/ 与 trace/ 目录创建完成
start live collectors
    -> dmesg -wT 追加写入 logs/host-dmesg-live.log
    -> journalctl -kf 追加写入 logs/host-journal-live.log
sync barrier
    -> 执行 sync，降低 host panic 前日志未刷盘风险
run risky action
    -> crosvm / host BAR touch / teardown stress
finalize if host survives
    -> status.json = COMPLETE / FAILED / INCONCLUSIVE
    -> 收集 final dmesg 与 trace snapshot
recover after crash/interruption
    -> 下一次运行先把遗留 RUNNING 标记为 CRASHED_OR_INTERRUPTED
    -> 保留 live logs 作为问题记录证据入口
```

`scripted` case 后续自动化时必须通过 harness 的 `run-shell` 或 `prepare-run` / collector 入口执行；不得直接绕过日志保全去调用 `scripts/run-crosvm.sh`。`run-shell` 默认会启动 live `dmesg -wT` / `journalctl -kf` collectors，再执行 action；`--no-host-collectors` 只能用于单元测试或明确低风险命令。

## 统一 forbidden signature

每个 runtime case 都应扫描 host 新增 `dmesg`。默认 forbidden signature：

```text
DMA Read NO_PASID
PTE Read access is not set
do_donate failed
host_initiate_donation: page refcounted
pkvm: exception
soft lockup
RCU stall
BUG:
general protection fault
kernel panic
```

`WARNING:` 默认不直接判 fail，但必须记录；若某轮目标是 PR 合入前严查，可在执行记录里把 `WARNING:` 提升为 fail 条件。

## P0 必跑用例

### T12-A1 protected VFIO attach 后 BAR revoke

| 字段 | 内容 |
|---|---|
| 模式 | `scripted` |
| 优先级 | P0 |
| 目的 | 验证 attach 阶段确实对受管理 BAR 执行 Host EPT revoke / annotation |
| 触发 | protected pVM + VFIO NVMe 启动到 guest login |
| 通过条件 | host 新增日志出现每个受管理 BAR 的 `pkvm: ptdev BAR revoked`；guest 能到 `login:` |
| 失败条件 | 未出现 revoke 日志；guest 早期失败；出现 forbidden signature |
| 证据 | host dmesg 节选、crosvm 串口日志、BDF 与 BAR index |

最小命令：

```bash
cd /home/mrgeek/pkvm-x86
date -u '+%F %T'
sudo -n env PROTECTED=1 SETUP_NET=0 VFIO_DEV=0000:01:00.0 ./scripts/run-crosvm.sh
sudo -n dmesg -T | grep -E 'ptdev BAR revoked|pkvm: exception|DMAR|IOMMU|soft lockup|RCU stall|BUG:'
```

预期关键日志：

```text
pkvm: ptdev BAR revoked bdf=0x... bar=... hpa=0x... size=0x...
```

### T12-A2a Host BAR deny-remap 被动观测

| 字段 | 内容 |
|---|---|
| 模式 | `agent-runbook` |
| 优先级 | P0 |
| 目的 | 验证 Host EPT 缺页命中 assigned BAR annotation 时拒绝 lazy remap |
| 触发 | 正常 protected pVM + VFIO attach；如果 host 自然触发 assigned BAR fault，则观察 deny-remap 结果 |
| 通过条件 | 出现 `pkvm: deny host BAR remap`；Host EPT 不重新 idmap 该 BAR；guest VFIO I/O 不被破坏 |
| 未命中条件 | 本轮没有 host 侧自然 BAR fault；记录为 `INCONCLUSIVE`，不判 fail |
| 失败条件 | 出现 host assigned BAR fault 后没有 deny；或 deny 后 guest direct BAR / VFIO I/O 被破坏 |
| 证据 | host dmesg、对应 BAR HPA/size、guest I/O 结果 |

说明：`deny host BAR remap` 是 T12 第一阶段的核心保护命中，不是异常现象。`T12-A2a` 是 passive check：只在正常运行过程中自然出现 Host BAR fault 时判定；如果没有自然触发，不说明实现失败。

预期关键日志：

```text
pkvm: deny host BAR remap gpa=0x... owner_id=... raw_pte=0x...
```

### T12-A2b Host BAR touch injection 主动触发

| 字段 | 内容 |
|---|---|
| 模式 | `agent-runbook` |
| 优先级 | P1 |
| 目的 | 主动触发 host 对 assigned BAR 的访问，证明 deny-remap 分支可被稳定命中 |
| 触发 | attach 后，由 host 侧通过 `/sys/bus/pci/devices/$BDF/resourceN` 或等价调试路径触碰已分配 BAR |
| 前置开关 | 需要执行者显式确认 `--allow-host-bar-touch` 或在验证记录中写明“允许 host BAR touch injection” |
| 通过条件 | 出现 `pkvm: deny host BAR remap`；Host EPT 不 lazy-remap BAR；guest 不崩；后续 NVMe 只读 I/O 仍成功 |
| 失败条件 | Host touch 后 BAR 被重新 idmap；guest 崩溃；出现 forbidden signature；设备需要物理复位才能恢复 |
| 证据 | 注入命令、resourceN 选择依据、host dmesg、guest 后续 I/O 结果、设备恢复状态 |

说明：`T12-A2b` 的危险点不是“deny-remap 现象”，而是测试手段会让 host 用户态或调试路径主动触碰一个已经交给 protected pVM 的设备 BAR。第一阶段默认不把它放入无确认的 scripted 回归；需要由 Codex 在 runbook 中明确记录触发命令、BAR 选择、执行窗口和恢复结果。

建议执行约束：

```text
1. 先完成 T12-A1 / T12-B1，确认 guest VFIO 正向路径可用。
2. 记录 host dmesg 起始时间与目标 BDF 的 resource map。
3. 只触碰一个明确属于受管理 memory BAR 的最小范围。
4. 触发后立即检查 deny-remap 日志。
5. 回到 guest 做只读 dd iflag=direct，确认设备仍可用。
6. 退出 VM 后检查 restore 与 forbidden signature。
```

### T12-C1 DMA view ready 后才发布 guest contract

| 字段 | 内容 |
|---|---|
| 模式 | `agent-runbook` |
| 优先级 | P0 |
| 目的 | 验证 guest DIRECT_BAR allowlist 不会早于 DMA view commit 发布 |
| 触发 | protected VFIO attach，同时采集 host trace / dmesg / guest allowlist 查询结果 |
| 通过条件 | BAR revoke 先发生；`pkvm_iommu_sync()` 成功后 `dma_view_ready=true`；随后 guest contract 才发布 |
| 失败条件 | metadata 早到时直接暴露 guest allowlist；或 guest 在 DMA view 未 ready 前命中 direct BAR |
| 证据 | host trace summary、guest direct MMIO trace、源码对照分析 |

建议观测点：

```text
pkvm_revoke_ptdev_bars_locked()
    -> pkvm_host_ept_annotate_mmio_owner()
pkvm_attach_ptdev()
    -> pkvm_iommu_sync()
    -> WRITE_ONCE(ptdev->dma_view_ready, true)
    -> pkvm_publish_ptdev_mmio_contract_locked()
```

当前代码没有专门打印 `dma_view_ready=true` 与 contract publish 日志；第一轮可用 kprobe/tracefs 观察函数顺序，或在验证记录中说明该 case 当前只能做到“函数命中顺序 + guest 行为”的间接证据。若后续需要稳定脚本化，建议补最小 debug 日志或 tracepoint。

### T12-B1 guest DIRECT_BAR direct MMIO 与 NVMe DMA 证据链

| 字段 | 内容 |
|---|---|
| 模式 | `agent-runbook` |
| 优先级 | P0 |
| 目的 | 验证 guest 侧 NVMe BAR MMIO 命中 direct 分支，且块设备 I/O 经过 DMA 建图路径 |
| 触发 | guest 内对 `/dev/nvme0n1` 做只读 direct I/O，并运行 T11 host/guest trace helper |
| 通过条件 | guest direct MMIO 计数 > 0；guest DMA map / NVMe submit 路径可见；host fallback MMIO 计数不增长或为 0 |
| 失败条件 | direct MMIO 计数为 0；host fallback MMIO 在 I/O 窗口明显增长；guest I/O 失败 |
| 证据 | T11 `guest-summary.txt`、`host-summary.txt`、guest `dd` 输出 |

guest 最小 I/O 命令：

```bash
ls -l /dev/nvme0n1
printf '\n' | sudo -S sh -c 'dd if=/dev/nvme0n1 of=/dev/null bs=4M count=8 iflag=direct status=none; echo DD_RC=$?'
```

证据链：

```text
guest dd iflag=direct
    -> nvme_queue_rq()
        -> nvme_map_data()
            -> dma_map_bvec() / dma_map_sgtable()
        -> nvme_write_sq_db()
            -> writel()
                -> pkvm_virt_mmio()
                    -> pkvm_direct_mmio_write()   [DIRECT_BAR]
                    -> mmio_write()               [fallback, 不应在本窗口明显增长]
```

| 字段 | 内容 |
|---|---|
| 模式 | `agent-runbook` |
| 优先级 | P0 |

## P1 负向 / 边界用例

### T12-N1 metadata 早到时缓存但不提前发布

| 字段 | 内容 |
|---|---|
| 模式 | `agent-runbook` |
| 优先级 | P1 |
| 目的 | 验证 metadata 可先缓存，但 guest allowlist 只能在 owner/DMA 条件满足后发布 |
| 触发 | 让 `SET_PTDEV_MMIO_METADATA` 早于 `dma_view_ready=true` 到达，或通过 trace 观察当前 crosvm 提交时序 |
| 通过条件 | metadata hypercall 返回成功；内部 `-EAGAIN` 不暴露给 userspace；guest direct BAR 不提前可用 |
| 失败条件 | allowlist 在 DMA view ready 前发布；metadata 早到导致 attach 失败 |
| 证据 | host trace、crosvm log、guest allowlist 查询结果 |

### T12-N2 metadata 幂等重复提交

| 字段 | 内容 |
|---|---|
| 模式 | `fault-injection-required` 或专用 userspace hook |
| 优先级 | P1 |
| 目的 | 验证相同 metadata 重复提交不会破坏状态 |
| 触发 | 同一 BDF/PASID 提交完全相同 metadata 两次 |
| 通过条件 | 第二次返回成功或继续尝试 publish；不重复污染 allowlist |
| 失败条件 | 返回 `-EBUSY`；旧状态被清空；guest direct BAR 消失 |
| 证据 | KVM_ENABLE_CAP 返回值、host trace、guest allowlist |

### T12-N3 metadata mismatch reject

| 字段 | 内容 |
|---|---|
| 模式 | `fault-injection-required` 或专用 userspace hook |
| 优先级 | P1 |
| 目的 | 验证已缓存 metadata 后，不同 generation/ranges/flags 被拒绝 |
| 触发 | 第一次提交合法 metadata，第二次提交不同 metadata |
| 通过条件 | 第二次返回 `-EBUSY`；旧 allowlist 保持不变 |
| 失败条件 | 新 metadata 覆盖旧 contract；guest 可见范围被 Host 运行期篡改 |
| 证据 | 返回值、前后 allowlist dump、host trace |

### T12-N4 metadata range 超出 manifest BAR

| 字段 | 内容 |
|---|---|
| 模式 | `fault-injection-required` 或专用 userspace hook |
| 优先级 | P1 |
| 目的 | 验证 metadata 的 `bar_offset + size` 必须落在 boot manifest BAR 内 |
| 触发 | 提交超出 BAR 边界的 DIRECT_BAR range |
| 通过条件 | 返回 `-EPERM`；不发布 guest allowlist |
| 失败条件 | 超范围 BAR 被发布给 guest |
| 证据 | KVM_ENABLE_CAP 返回值、host dmesg、guest allowlist |

### T12-N5 metadata kind 非 DIRECT_BAR

| 字段 | 内容 |
|---|---|
| 模式 | `fault-injection-required` 或专用 userspace hook |
| 优先级 | P1 |
| 目的 | 验证第一阶段只接受 `KVM_PROTECTED_VM_PTDEV_MMIO_KIND_DIRECT_BAR` |
| 触发 | 提交非 DIRECT_BAR kind |
| 通过条件 | 返回 `-EINVAL`；不发布 guest allowlist |
| 失败条件 | 非 DIRECT_BAR range 进入 guest contract |
| 证据 | 返回值、host trace、guest allowlist |

### T12-N6 boot manifest miss 的 protected attach 被拒绝

| 字段 | 内容 |
|---|---|
| 模式 | `agent-runbook` |
| 优先级 | P1 |
| 目的 | 验证不在 boot manifest 中的设备不能进入 protected ptdev attach / BAR contract |
| 触发 | 复用 hot-add BDF 或 boot 后才出现的 BDF |
| 通过条件 | protected attach 被拒绝；普通 VM legacy path 不被误伤 |
| 失败条件 | protected pVM 接受 manifest miss 设备；或普通 VM 被错误拒绝 |
| 证据 | host dmesg、crosvm log、BDF 出现时序 |

## P2 故障注入用例

### T12-F1 BAR revoke 部分失败回滚

| 字段 | 内容 |
|---|---|
| 模式 | `fault-injection-required` |
| 优先级 | P2 |
| 目的 | 验证 `pkvm_host_ept_annotate_mmio_owner()` 某个 BAR 失败后，已 touched BAR 能恢复 |
| 注入点 | `pkvm_host_ept_annotate_mmio_owner()` 或 `pkvm_pgtable_annotate()` |
| 通过条件 | 已 touched BAR restore；`touched_bar_mask` 清零；owner 回 HOST；attach 返回失败 |
| 失败条件 | 半 revoke 状态残留；后续 host / guest BAR 视图不一致 |
| 证据 | 注入配置、host dmesg、状态 dump |

### T12-F2 C 阶段 `pkvm_iommu_sync()` 失败回滚

| 字段 | 内容 |
|---|---|
| 模式 | `fault-injection-required` |
| 优先级 | P2 |
| 目的 | 验证 A 成功后 C 失败时，BAR restore、ptdev unlink、`shadow_vm_handle=0` 都能完成 |
| 注入点 | attach 路径中的 `pkvm_iommu_sync(ptdev->bdf, ptdev->pasid)` |
| 通过条件 | restore 成功；`dma_view_ready=false`；guest contract 未发布；VFIO 后续可重试 |
| 失败条件 | restore 失败；ptdev 仍挂在 VM 链表；后续 VFIO group busy |
| 证据 | 注入配置、host dmesg、重复 attach 结果 |

### T12-F3 未 quiesce 时 restore busy

| 字段 | 内容 |
|---|---|
| 模式 | `fault-injection-required` |
| 优先级 | P2 |
| 目的 | 验证 `dma_view_ready=true` 且未证明 DMA unreachable 时，restore 返回 `-EBUSY` 并保留状态 |
| 注入点 | 跳过或延迟 `pkvm_quiesce_ptdev()` 后触发 detach restore |
| 通过条件 | `pkvm_restore_ptdev_bars_locked()` 返回 `-EBUSY`；detach 不继续 unlink/sync/put |
| 失败条件 | 未 quiesce 就恢复 Host BAR idmap；DMA 仍可达时 host 重新可访问 BAR |
| 证据 | 注入配置、host dmesg、状态 dump |

## 第一轮执行建议

第一轮不追求一次性覆盖 P1/P2，建议按下面顺序执行：

1. `T12-G2`：protected pVM 无 VFIO baseline。
2. `T12-G1`：普通 VM + VFIO baseline。
3. `T12-A1`：protected pVM + VFIO attach/revoke。
4. `T12-B1`：guest direct MMIO + DMA 证据链。
5. `T12-R1`：clean poweroff restore。
6. `T12-G3`：重复 boot/destroy 3 轮。
7. `T12-A2a`：正常运行中被动观察 Host BAR deny-remap；未自然触发则记录为 `INCONCLUSIVE`。
8. `T12-C1` / `T12-R2`：由 Codex 做源码对照 + trace 证据补强。
9. `T12-A2b`：仅在确认允许 host BAR touch injection 后主动触发 deny-remap。

若任意步骤出现新 panic / fault / 稳定报错签名，应停止继续扩大矩阵，按本仓库规则新建独立 `Bug` issue 和本地问题记录。
