- 已确认当前代码里已经存在 `pgstate_pgt -> ptdev->pgt -> IOMMU SLPTR` 这条骨架，但缺少预填充、运行时 mirror、teardown 收敛等关键补全。
- 已建立 `实施跟踪/` 目录，后续实施拆分、依赖关系、状态推进和验证矩阵统一在该目录维护。

当前卡点:
- `BOOT-007` 已完成更高置信度归因：官方 issue `#46` 与本地 `arch/x86/coco/pkvm/pkvm.c` 一致表明，当前分支里的 protected pVM 设备透传本身尚未真正支持。
- 当前更深的前置阻塞不是单纯的 crosvm config/MMIO fallback，而是 pVM guest 把所有 MMIO 都走 hypercall，无法直接访问直通设备物理 MMIO。
- 当前 host->pKVM 透传设备接口也只传 `BDF/PASID`，没有传 BAR/MMIO 资源元数据；因此主线还缺一层设备信息 contract。
- 已确认 ARM64 pKVM/AVF 可以作为重要参考对象，但参考重点应放在：
  - device metadata / manifest 通道
  - guest MMIO 分类机制
  - pKVM/hyp 持有 authoritative device state
  - 而不是直接照搬 ARM 的设备 assignment 代码路径
- 已新增 ARM 参考源清单，并约定后续本地参考代码统一落在未跟踪的 `refs/` 目录：
  - `DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/参考实现/ARM-pKVM-参考源.md`
- 已基于本地 ARM 参考树整理出一版设计映射：
  - `DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/参考实现/ARM-pKVM-到-x86-设计映射表.md`
- B3 已收敛出一个更合适的推进方式：先做“上层方案收敛”，再继续细化底层 contract。
- 当前倾向的低复杂度第一阶段目标是：
  - protected pVM
  - 单个 VFIO PCI 设备
  - 静态 attach
  - `NoIommu`
  - config space 继续 emulated
  - 普通 BAR MMIO 作为优先打通的访问面
  - MSI-X table/PBA 继续 emulate 或列为第一阶段非目标
- 在这个上层方案稳定后，B3 再继续细化：
  - 以“受信的 GPA 直达区间表”作为 guest/hyp contract
  - userspace -> host KVM：复用 `KVM_CAP_X86_PROTECTED_VM` 的 `KVM_ENABLE_CAP` flag 空间提交候选区间表
  - authoritative allowlist：必须最终存放在 pKVM/hyp，而不是停留在 host KVM
  - guest -> pKVM/hyp：使用“共享缓冲区 + 分块 hypercall 拷贝”查询直达区间表
  - 注册项至少携带 `guest_gpa + bdf + pasid + bar_index + bar_offset + size + flags`
- B3-1 上层方案已单独沉淀到：
  - `DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/01C-1-B3-1-protected-pVM-设备透传第一阶段上层方案.md`
- B3-2 已开始细化第一阶段所需的 x86 `ptdev metadata` 结构，当前方向是：
  - `ptdev` 继续承载 identity / IOMMU / attachment state
  - 新增 hyp 内部的富 MMIO metadata
  - guest 只获取精简 allowlist
  - 文档：`DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/01C-2-B3-2-x86-ptdev-metadata-最小结构草案.md`
  - 当前接口方向：
    - userspace -> host KVM：继续沿用 `KVM_ENABLE_CAP(KVM_CAP_X86_PROTECTED_VM)`
    - guest -> pKVM/hyp：新增查询 allowlist 的 guest hypercall
  - 当前 ABI 决议：
    - metadata 必须在第一次 `KVM_RUN` 前提交
    - 第一阶段冻结 metadata，不支持运行期修改
    - guest 启动早期查询并缓存 allowlist
    - guest allowlist 只暴露 `DIRECT_BAR`
  - 当前已进一步收敛：
    - 推荐 UAPI 常量名与结构体命名
    - 提交接口与查询接口的错误码
    - 幂等提交语义
- B2 目前降级为候选 workaround，只用于实验性验证失败点能否继续后移。
- `pgstate_pgt` 当前还带有“pVM teardown 时 undonate 页面”的旧语义，需要收敛成纯 DMA mirror 语义。
- VM 销毁阶段当前是“先销毁页表，再处理 ptdev”，且现有 `pkvm_detach_ptdev()` 实际是切回 host IOMMU 视图，不等于真正 quiesce 设备 DMA。
- `failed to create vm mapping (EINVAL)` 仍然是重要前置信号；当前本地 crosvm 之所以会先打到这里，还叠加了 x86_64 `is_pkvm()` 误报能力的 correctness 问题。
