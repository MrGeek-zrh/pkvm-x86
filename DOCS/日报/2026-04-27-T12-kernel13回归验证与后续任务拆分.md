## 今日目标

## 过程记录

### 阶段一：先拆 review follow-up，不把 #36 继续膨胀

#### 现象

#36 首版修复已经把 Host BAR revoke 从整 BAR 改成 `DIRECT_BAR` range，但代码 review 后发现还有几类语义风险不应塞进 #36 的当前 B0 修复目标里：

- map-side 只校验 HPA 命中 `DIRECT_BAR` range，还没有同时校验 guest GPA 是否等于 metadata 发布的 `guest_gpa + offset`。
- BAR resource preparation 失败时可能残留半初始化 `ptdev->bars[]` / `managed_bar_mask`。
- 未被 metadata 使用的 sub-page BAR 可能因为 manifest 全 BAR 页对齐检查而误伤 attach。
- guest EPT map-side 可能在 contract 尚未发布完成前，只凭 `dma_view_ready` 提前放行。
- Host EPT annotation 如果半成功后失败，当前 range 的部分 annotation 可能没有进入 restore 列表。

这些不是同一条 panic 签名，也不是 #35 的第一 blocker 修复条件。

#### 处理

按“问题、动作、集成分离”的规则，把它们拆成独立 Task：

- MrGeek-zrh/pkvm-x86#39：map-side 强制 `DIRECT_BAR` guest GPA contract。
- MrGeek-zrh/pkvm-x86#40：BAR resource preparation 失败路径清理半初始化状态。
- MrGeek-zrh/pkvm-x86#41：`DIRECT_BAR` 校验避免误拒绝未使用 sub-page BAR。
- MrGeek-zrh/pkvm-x86#42：guest EPT `DIRECT_BAR` map 必须等待 contract 发布完成。
- MrGeek-zrh/pkvm-x86#43：Host EPT annotation 失败路径回滚部分 `DIRECT_BAR` range。

同时在 MrGeek-zrh/pkvm-x86#36 comment 中回链这些 follow-up，明确 #36 当前仍聚焦 #35：保留 MSI-X table / PBA Host 控制面，并把 Host BAR revoke 细化到 guest `DIRECT_BAR` 数据面范围。

#### 结果

当天没有把 #39-#43 作为 #36 的合入前置条件，也没有把这些 follow-up 混成新的大任务。它们都还是 `status/triage`，后续进入实际实现前，如果方案展开超过 issue 摘要，需要再补本地 `DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/` 设计或验证文档。
