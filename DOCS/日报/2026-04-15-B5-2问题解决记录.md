# 2026 年 4 月 15 日 — B5-2 问题解决记录

## B5-2 的核心目标

B5 有两个子问题：

1. **问题 1**：不在启动期 manifest 名单里的设备，不允许透传给 pVM。（对应 T9，已完成）
2. **问题 2**：Host 不可信前提下，hyp 必须能校验 Host 传进来的 HPA 是否落在当前 VM attached 设备的合法 BAR 范围内。

本文只记录问题 2 的解决过程。

问题 2 的核心挑战是：

- pVM 透传了一个 NVMe 设备，guest 访问 NVMe BAR 的某个 GPA
- host 侧 KVM 在缺页异常处理中把这个 GPA 翻译成一个 HPA
- hyp 收到这个 HPA 后要把它装入 Guest EPT
- 如果 hyp 没有校验能力，Host 可以传任意 HPA，这是安全隐患

所以 hyp 必须能判断：这个 HPA 确实在当前 VM attached 设备的 memory BAR 范围内。如果不在，hyp 必须拒绝。

---

## 迭代过程

### 目标：实现 HPA 安全校验

核心要实现的就是一件事：host 传进来的 `[hpa, hpa + size)` 要经过 hyp 校验，确认它落在当前 VM attached 的某个 memory BAR 范围内。不在范围内 → 拒绝。落在范围内 → 允许并建 Guest EPT leaf（不走 donate）。

具体分两条路径：

**路由决策**（这条比较直接）：
- BAR HPA 不是 RAM，本来就不应该走 donate 路径。命中 BAR → 直接 MMIO leaf 建图，teardown 时只拆 EPT 不调 undonate。

**安全校验**（这条是核心）：
- 启动期在 host 侧遍历所有 PCI 设备，把每个设备的 memory BAR 记录到 boot-time manifest
- hyp 提供 helper：`pkvm_vm_hpa_hits_attached_boot_ptdev_bar(kvm, hpa, size)`，在校验路径里调用

但在推进这个目标的过程中，遇到了几个没有预期到的 bug。

### Bug 1（绊脚石）：crosvm boot 路径没有提交 metadata

2026-04-15 跑 protected pVM + VFIO NVMe 样例，发现 metadata ioctl 根本没命中——`pkvm_mmio_allow_hit()` 永远返回 0。

追进去看 crosvm 代码，发现 boot 阶段的 PCI 设备走的是 `generate_pci_root()`，而不是有 metadata 提交逻辑的 `configure_pci_device()`。metadata 提交流程在启动路径里根本没调用。

修了两个地方：

- `crosvm/arch/src/lib.rs`：`generate_pci_root()` 补齐 boot-time metadata 提交流程，加上对 `set_protected_vm_ptdev_mmio_metadata()` 的调用
- `crosvm/hypervisor/src/kvm/x86_64.rs`：metadata ABI 结构体字段对齐到当前内核 UAPI

修完之后，`pkvm_vm_ioctl_set_ptdev_mmio_metadata()` 才命中，HPA 校验逻辑才有机会真正执行。

### Bug 2（新签名 BOOT-012）：HPA 进了 donate 路径

metadata 通了之后立刻暴露新签名：

```text
pkvm: host_initiate_donation: addr not in mem_range addr=0xfe800000 size=0x1000 owner_id=1
pkvm: __pkvm_host_donate_guest failed ret=-1 hpa=0xfe800000 gpa=0xd0000000 size=0x1000 prot=0x77
kvm: pkvm: vm_mmu_map failed ret=-1 gpa=0xd0000000 hpa=0xfe800000 size=0x1000 writable=1 goal_level=1 pfn=0xfe800
```

`0xfe800000` 是这块 NVMe 的 BAR0 起始地址，不是普通内存。

追调用链：

```text
guest 访问 NVMe BAR GPA
    host KVM 缺页路径解析出 HPA = 0xfe800000（BAR0 起始地址）
        pkvm_hypercall(vm_mmu_map, gpa, hpa, size, ...)
            guest_mmu_map_leaf()
                __pkvm_host_donate_guest(hpa, ...)
                    do_donate()
                        host_initiate_donation()
                            find_mem_range(hpa, &range)
                                // BAR 地址不在 host RAM mem_range 里
                                // 失败，返回 addr not in mem_range
```

根因：`guest_mmu_map_leaf()` 在建图前没有判断这个 HPA 是不是 BAR 地址，直接就进了 donate 路径。PCI BAR 地址不在 host RAM 的 mem_range 里，所以必然失败。

这暴露了一个问题：路由决策和校验逻辑在实现前就已经存在——必须先解决 BAR HPA 不走 donate 路径，才能让 HPA 校验逻辑有机会执行。

对应内核 commit：`501ca0cb907f`

具体做了 4 件事：

**1. 扩展 boot-time manifest，记录每个设备的 memory BAR**

`pKVM-IA/arch/x86/kvm/vmx/pkvm/include/pkvm.h` 扩展 `struct pkvm_boot_ptdev_manifest_entry`，新增 `bars[]` 数组记录 `base` 和 `size`。`pKVM-IA/arch/x86/kvm/vmx/pkvm/pkvm_host.c` 的 `build_boot_ptdev_manifest()` 启动时遍历所有 PCI 设备，把每个设备的 memory BAR 全部存进去。

**2. 提供 HPA 是否命中 BAR 的统一 helper**

`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ptdev.c` 里新增 `pkvm_boot_ptdev_bar_contains()`：

```text
命中条件：
    hpa >= bar_base
    hpa + size <= bar_base + bar_size
```

封装成两个对外函数：

- `pkvm_host_hpa_hits_boot_ptdev_bar(hpa, size)` — 在全量 boot manifest 里查，不管有没有 attach 给 VM
- `pkvm_vm_hpa_hits_attached_boot_ptdev_bar(kvm, hpa, size)` — 只在当前 VM attached 的设备里查

**3. `pkvm_vm_mmu_map()` 中做三段分流**

`pKVM-IA/arch/x86/kvm/pkvm/mmu.c` 里 `pkvm_vm_mmu_map()` 在正式建图前先判断：

```text
if (命中当前 VM attached BAR) {
    // 路由决策 + 安全校验通过：直接 MMIO leaf 建图
    // 不走 __pkvm_host_donate_guest()
    pgtable_map_leaf(...)
} else if (命中 host RAM mem_range) {
    // 普通 RAM：走 donate 路径
    __pkvm_host_donate_guest(...)
} else {
    // 安全校验失败：既不是 BAR 也不是 RAM，直接拒绝
    return -EPERM
}
```

同时 `guest_mmu_map_leaf()` 里也加了一次判断，命中 BAR 时直接跳到 `pgtable_map_leaf()`，不走 donate。

**4. teardown 时跳过 BAR leaf 的 undonate**

`guest_mmu_free_leaf()` 里，如果 leaf 命中 BAR 范围，只拆 Guest EPT leaf，不调 `__pkvm_host_undonate_guest()`。

改动文件：
- `pKVM-IA/arch/x86/kvm/pkvm/mmu.c` — 建图时分流，teardown 时跳过 undonate
- `pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ptdev.c` — 提供 BAR 范围命中判断的 helper
- `pKVM-IA/arch/x86/kvm/vmx/pkvm/include/pkvm.h` — 扩展 manifest 记录 memory BAR 的 base/size
- `pKVM-IA/arch/x86/kvm/vmx/pkvm/pkvm_host.c` — 启动期收集 BAR 数据

### Bug 3（新签名 BOOT-013）：pin 语义不适用于 BAR/MMIO PFN

安装了包含 `501ca0cb907f` 的新内核后，protected pVM 出现了新签名：

```text
[ERROR crosvm::crosvm::sys::linux::vcpu] vcpu hit unknown error: Bad address (os error 14)
[WARNING: CPU: 18 PID: 4255 at arch/x86/kvm/mmu/mmu.c:4775 kvm_tdp_page_fault+0x3f0/0x420]
```

追调用链：

```text
guest 访问 NVMe BAR GPA
    host KVM 缺页解析出 BAR HPA
        pkvm_page_fault()
            pkvm_hypercall(vm_mmu_map, gpa, hpa, size, ...)
                // BOOT-012 修复后：命中 BAR 直接建 Guest EPT leaf（成功）
            pkvm_pin_page(vcpu->kvm, fault)
                kvm_pfn_to_refcounted_page(fault->pfn)
                    // BAR/MMIO PFN 不是普通 RAM，没有 refcounted struct page
                    return NULL
                WARN_ON_ONCE(!page)
                return -EFAULT
        KVM_RUN 返回 -EFAULT
```

根因：host-high 的 `pkvm_page_fault()` 在建图成功后，对 protected VM 会无条件调 `pkvm_pin_page()` 把 host 页 pin 住，防止被回收或迁移。这对普通 RAM 是对的，但对 BAR/MMIO PFN 来说，`kvm_pfn_to_refcounted_page()` 返回 NULL，所以 `WARN_ON_ONCE` 触发并返回 `-EFAULT`。

解决方案是：在 `pkvm_page_fault()` 里对 `pkvm_pin_page()` 加一个保护，如果 `kvm_pfn_to_refcounted_page()` 返回 NULL，就跳过 pin 而不是报警失败。

对应内核 commit：`efba4f386b27`

改动文件：
- `pKVM-IA/arch/x86/kvm/mmu/mmu.c` — `pkvm_page_fault()` 中对 non-refcounted PFN 跳过 pin

## 暂时未解决的问题

### 问题 A：`pvmfw` GPA 路径还没排除 direct BAR HPA

当前 `pkvm_vm_mmu_map()` 已经允许命中 BAR 的 HPA 走 direct leaf 建图，但 `load_pvmfw()` / `gpa_range_overlaps_pvmfw()` 路径还没排除掉 direct BAR HPA。

这意味着如果 host 把某个 attached BAR 映到 `pvmfw` GPA，当前实现存在把 `pvmfw` 内容写入 BAR/MMIO 的风险。

本轮先记录，后续需要单独决定是：
- 拒绝 `direct_mmio && gpa_range_overlaps_pvmfw()`
- 还是把 `load_pvmfw()` 明确限制为 host RAM 路径

### 问题 B：host `kvm_sev_es_mmio_write` 计数还有残余

修复后 host `kvm_sev_es_mmio_write` 里仍有写事件，但 guest 侧 `pkvm_virt_mmio()` trace 已经把 `dd` 任务本身钉在 `direct_hit`。

这些 host write 事件不来源于这次 NVMe `dd` 的 MMIO 访问，而是来自 guest 生命周期中其他来源（比如 MSI-X 中断处理、固件访问等），需要后续单独分类。

### 问题 C：本轮不检查 BAR 内 offset

当前验收标准只要求 `[hpa, hpa + size)` 完整落在 boot-time manifest 记录的某个 memory BAR 内，不检查 BAR 内 offset 是否和 guest GPA 对应。同一 BAR 范围内 guest 访问不同 offset 都被认为合法。

本轮不处理，后续如果需要更严格的安全边界再单独评估。
