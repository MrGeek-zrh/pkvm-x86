# 2026 年 4 月 15 日 — B5-2 问题解决记录

## 今日目标

把 B5-2 的主线收敛清楚：让 hyp 能独立判断 host 传进来的 `[hpa, hpa + size)` 是否落在当前 VM 已 attach 设备的合法 memory BAR 范围里；命中才允许建图，不命中就拒绝。

## 过程记录

### 阶段一：发现 boot-time metadata 根本没提交

#### 现象

在 protected pVM + VFIO NVMe `0000:01:00.0` 样例里，guest 对 NVMe BAR 的访问没有命中 direct MMIO allowlist，关键输出是：

```text
BASE_DIRECT=0
BASE_FALLBACK=2
DD_DIRECT=0
DD_FALLBACK=130
allow_obs: ... gpa=0xd0001008 end=0xd000100c nr=0 info=0x0 ranges={0x0,0x0,0x0,0x0,0x0,0x0,0x0,0x0,0x0}
allow_obs: ... gpa=0xd000100c end=0xd0001010 nr=0 info=0x0 ranges={0x0,0x0,0x0,0x0,0x0,0x0,0x0,0x0,0x0}
```

最小影响是：B5-2 的 HPA 范围校验逻辑还没真正跑起来，先卡在 crosvm 启动期没有把 metadata 送进内核。

#### 根因

追启动路径后确认，boot 阶段的 PCI / VFIO 设备走的是 `crosvm/arch/src/lib.rs` 里的 `generate_pci_root()`，而 metadata 提交流程只在 `configure_pci_device()` 里。

调用链是：

```text
x86_64 启动流程
    -> arch::generate_pci_root(pci_devices, ...)
        -> 当前没有 metadata 查询 / 提交逻辑

另一条已有逻辑的路径
    -> configure_pci_device()
        -> device.get_protected_vm_ptdev_mmio_metadata(&linux.vm)
        -> linux.vm.set_protected_vm_ptdev_mmio_metadata(&metadata)
```

所以这时不是 hyp 判错了，而是 crosvm 根本没把 boot-time VFIO 设备的 metadata 提交下去。

#### 解决方案

- 在 `crosvm/arch/src/lib.rs` 的 `generate_pci_root()` 补齐 boot-time metadata 提交流程
- 在 `crosvm/hypervisor/src/kvm/x86_64.rs` 把 metadata ABI 结构体字段对齐到当前内核 UAPI

#### 结果

补完后，host trace 已经能看到 metadata ioctl 真正命中：

```text
enable_cap: (pkvm_vm_ioctl_enable_cap+0x0/0x170)
meta_enter: (pkvm_vm_ioctl_set_ptdev_mmio_metadata+0x0/0x3e0)
enable_cap: (pkvm_vm_ioctl_enable_cap+0x0/0x170)
```

到这一步，B5-2 才从"用户态没送数据"推进到"kernel / hyp 真正收到 HPA，开始暴露运行期问题"。

### 阶段二：落地 B5-2 本体——HPA 范围判定

#### 现象

metadata 打通以后，hyp 已经能收到 host 传进来的 candidate HPA，但当时还没有自己的 BAR 范围真相源。换句话说，host 如果传任意 HPA，hyp 还不能只靠自己判断"这个 HPA 是不是当前 VM 已 attach 设备的合法 memory BAR"。

#### 根因

问题不在单一函数，而在信息缺口：

- `pKVM-IA/arch/x86/kvm/vmx/pkvm/include/pkvm.h` 里的 boot-time manifest 之前只够表达设备名单，不够表达每个设备的 memory BAR 范围
- `pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ptdev.c` 里也没有统一 helper 去判断 `[hpa, hpa + size)` 是否命中"当前 VM 已 attach 设备"的某个 BAR

所以 hyp 之前只能知道"这是 host 传来的 HPA"，却不知道"这个 HPA 对当前 VM 来说是不是合法 BAR 地址"。

#### 解决方案

对应内核 commit：`501ca0cb907f`

这一步里和"范围判定"直接相关的改动是：

- `pKVM-IA/arch/x86/kvm/vmx/pkvm/include/pkvm.h`：扩展 `struct pkvm_boot_ptdev_manifest_entry`，新增 `bars[]`，记录每个 memory BAR 的 `base` 和 `size`
- `pKVM-IA/arch/x86/kvm/vmx/pkvm/pkvm_host.c`：在 `build_boot_ptdev_manifest()` 启动期遍历 PCI 设备，把 memory BAR 数据写进 manifest
- `pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ptdev.c`：新增 `pkvm_boot_ptdev_bar_contains()`、`pkvm_host_hpa_hits_boot_ptdev_bar()`、`pkvm_vm_hpa_hits_attached_boot_ptdev_bar()`，统一做 BAR 命中判断
- `pKVM-IA/arch/x86/kvm/pkvm/mmu.c`：把"当前 HPA 是否命中当前 VM attached BAR"接进建图前的校验路径

解决方案对应的调用栈可以拆成两段看：

```text
启动期先把 boot-time BAR 真相源做出来
    __vmx_pkvm_init() (pKVM-IA/arch/x86/kvm/vmx/pkvm/pkvm_host.c)

            build_boot_ptdev_manifest(pkvm) (pKVM-IA/arch/x86/kvm/vmx/pkvm/pkvm_host.c)

                    guest_mmu_is_host_ram_hpa(hpa, size) (pKVM-IA/arch/x86/kvm/pkvm/mmu.c)
                    if (!direct_mmio && !host_ram)
                        if pkvm_host_hpa_hits_boot_ptdev_bar(hpa, size) (pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ptdev.c)
                            是可信设备，但是不是attach给pVM的设备，拒绝map
                        else
                            hpa不在可信设备的BAR区域内，拒绝
```

### 阶段三：验证时暴露 BOOT-012——合法 BAR HPA 误进 donate 路径

#### 现象

metadata 命中以后，马上暴露出新的运行时签名：

```text
pci 0000:01:00.0: BAR 0 [mem 0xfe800000-0xfe803fff 64bit]
pkvm: host_initiate_donation: addr not in mem_range addr=0xfe800000 size=0x1000 owner_id=1
pkvm: __pkvm_host_donate_guest failed ret=-1 hpa=0xfe800000 gpa=0xd0000000 size=0x1000 prot=0x77
kvm: pkvm: vm_mmu_map failed ret=-1 gpa=0xd0000000 hpa=0xfe800000 size=0x1000 writable=1 goal_level=1 pfn=0xfe800
```

这里的 `0xfe800000` 明明就是 NVMe 的 BAR0 起始地址，不是普通 RAM。

#### 根因

追调用链后可以看到，问题已经不是"判不出 BAR 范围"，而是"命中合法 BAR 以后还沿着普通 RAM donation 语义继续往下走"：

```text
guest 访问 NVMe BAR GPA
    host KVM 缺页路径解析出 HPA = 0xfe800000
        pkvm_hypercall(vm_mmu_map, gpa, hpa, size, ...)
            guest_mmu_map_leaf()
                __pkvm_host_donate_guest(hpa, ...)
                    do_donate()
                        host_initiate_donation()
                            find_mem_range(hpa, &range)
                                // BAR 地址不在 host RAM mem_range 里
                                // 返回 addr not in mem_range
```

两件事相关，但不是一件事：
- HPA 范围判定：解决"这个 HPA 对当前 VM 来说合不合法"
- donate 分流：解决"命中合法 BAR 以后，该走 direct BAR leaf，还是走普通 RAM donation"

#### 解决方案

对应内核 commit：`501ca0cb907f`（同一个 commit 里还包含 donate 分流修正）

这一步里和 BOOT-012 直接相关的改动是：

- `pKVM-IA/arch/x86/kvm/pkvm/mmu.c`：在 `pkvm_vm_mmu_map()` / `guest_mmu_map_leaf()` 里把 BAR leaf 和普通 RAM leaf 分流；命中 BAR 时直接走 MMIO leaf 建图，不再调用 `__pkvm_host_donate_guest()`
- `pKVM-IA/arch/x86/kvm/pkvm/mmu.c`：在 `guest_mmu_free_leaf()` 里对 BAR leaf 只拆 Guest EPT，不再调用 `__pkvm_host_undonate_guest()`

路由口径是：

```text
命中当前 VM attached BAR
    -> direct MMIO leaf 建图
    -> teardown 时只拆 Guest EPT

命中 host RAM mem_range
    -> 继续走普通 RAM donation / undonation 语义
```

#### 结果

安装包含 `501ca0cb907f` 的新内核后，旧 BOOT-012 签名不再出现：

- 不再看到 `host_initiate_donation: addr not in mem_range`
- 不再看到 `__pkvm_host_donate_guest failed`
- 不再看到 `vm_mmu_map failed`

主线阻塞从 BOOT-012 前移到了下一层 host-high 后处理路径。

### 阶段四：BOOT-012 消失后暴露 BOOT-013——BAR/MMIO PFN 不适合普通 pin 语义

#### 现象

安装包含 `501ca0cb907f` 的内核后，protected pVM 又出现了新的签名：

```text
[ERROR crosvm::crosvm::sys::linux::vcpu] vcpu hit unknown error: Bad address (os error 14)
[WARNING: CPU: 18 PID: 4255 at arch/x86/kvm/mmu/mmu.c:4775 kvm_tdp_page_fault+0x3f0/0x420]
```

最小影响是：旧的 donation 签名没了，但 guest 还是起不来，新的主阻塞变成了 host-high 的 pin 后处理。

#### 根因

调用链如下：

```text
guest 访问 NVMe BAR GPA
    host KVM 缺页解析出 BAR HPA
        pkvm_page_fault()
            pkvm_hypercall(vm_mmu_map, gpa, hpa, size, ...)
                // BOOT-012 修复后：命中 BAR 直接建 Guest EPT leaf
            pkvm_pin_page(vcpu->kvm, fault)
                kvm_pfn_to_refcounted_page(fault->pfn)
                    // BAR/MMIO PFN 不是普通 RAM，没有 refcounted struct page
                    return NULL
                WARN_ON_ONCE(!page)
                return -EFAULT
```

`pkvm_vm_mmu_map()` 这边已经允许 BAR 直建图了，但 host-high 的 `pkvm_page_fault()` 还沿用"建图成功后一定要 pin 普通 RAM page"的旧假设。这对 BAR/MMIO PFN 不成立。

#### 解决方案

对应内核 commit：`efba4f386b27`

改动文件：
- `pKVM-IA/arch/x86/kvm/mmu/mmu.c`：在 `pkvm_page_fault()` 里给 `pkvm_pin_page()` 加保护；如果 `kvm_pfn_to_refcounted_page()` 返回 `NULL`，就跳过 pin，而不是 `WARN_ON_ONCE` 后返回 `-EFAULT`

#### 结果

安装包含 `efba4f386b27` 的内核后，重新跑同一条样例：

```text
DD_RC=0
DD_BIG_RC=0
GUEST_DIRECT=128
GUEST_FALLBACK=2
```

同时确认：
- protected pVM 成功启动到 `login:`，并可以登录 `ubuntu`
- guest 内 `nvme0n1` 正常枚举
- `dd` 窗口里的 `pkvm_virt_mmio()` 打点已经以 `direct_hit` 为主，`fallback_hit` 只剩两条 `sleep` 进程噪音
- host `dmesg` 不再出现 `Bad address`、`kvm_tdp_page_fault`、`pkvm_pin_page`、`host_initiate_donation: addr not in mem_range`、`vm_mmu_map failed`

## 今日未完成

- `pvmfw` GPA 路径还没排除 direct BAR HPA：`load_pvmfw()` / `gpa_range_overlaps_pvmfw()` 还没决定是直接拒绝，还是限制成只能走 host RAM 路径。
- host `kvm_sev_es_mmio_write` 残余事件还没分类：当前只确认 `dd` 对应窗口已经走 direct path，剩余 write 事件来源还没拆干净。
- BAR 内 offset 一致性还没检查：本轮只做到"命中合法 BAR 范围"，还没有把 guest GPA 和 BAR offset 做精确绑定。
