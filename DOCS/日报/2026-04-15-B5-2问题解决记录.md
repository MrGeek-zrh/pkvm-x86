# 2026 年 4 月 15 日 — B5-2 问题解决记录

## 这个问题是什么

B5 有两个子问题：

1. **问题 1**：不在启动期 manifest 名单里的设备，不允许透传给 pVM。（对应 T9，已完成）
2. **问题 2**：protected pVM 的 Guest EPT 建图时，Host 传进来的 HPA（物理地址）到底受不受 hyp 约束。

本文只记录问题 2 的解决过程。

问题 2 的核心是说：

- pVM 透传了一个 NVMe 设备，guest 访问 NVMe BAR 的某个 GPA（虚拟地址）
- host 侧 KVM 在缺页异常处理中把这个 GPA 翻译成一个 HPA（物理地址）
- hyp 收到这个 HPA 后，要把它装入 Guest EPT
- 但问题是：这个 HPA 是 PCI BAR 地址（不是普通内存地址），hyp 能不能判断"这个 HPA 确实就是这个设备 BAR 里的合法地址"？

如果 hyp 没有这个判断能力，那 Host 就可以传任意 HPA 进去，这是安全隐患。

---

## 解决过程

### 第一阶段：先发现 crosvm 没提交 metadata

2026-04-15 跑 protected pVM + VFIO NVMe 样例，最初发现 metadata ioctl 根本没命中数——`pkvm_mmio_allow_hit()` 永远返回 0。

追进去看 crosvm 代码，发现 boot 阶段的 PCI 设备走的是 `generate_pci_root()`，而不是有 metadata 提交逻辑的 `configure_pci_device()`——metadata 提交流程在启动路径里根本就没调用。

修了两个地方：

- `crosvm/arch/src/lib.rs` 里 `generate_pci_root()` 补齐了和 `configure_pci_device()` 对齐的 boot-time metadata 提交流程——原来 boot 阶段 PCI 注册路径根本没有调用 `set_protected_vm_ptdev_mmio_metadata()`，现在补上了
- `crosvm/hypervisor/src/kvm/x86_64.rs` 里 metadata 的 ABI 布局对齐到当前内核 UAPI，结构体字段对上了

修完之后，`pkvm_vm_ioctl_set_ptdev_mmio_metadata()` 终于命中了。

### 第二阶段：metadata 通了，但出现 BOOT-012

metadata 通了之后立刻暴露新签名：

```text
pkvm: host_initiate_donation: addr not in mem_range addr=0xfe800000 size=0x1000 owner_id=1
pkvm: __pkvm_host_donate_guest failed ret=-1 hpa=0xfe800000 gpa=0xd0000000 size=0x1000 prot=0x77
kvm: pkvm: vm_mmu_map failed ret=-1 gpa=0xd0000000 hpa=0xfe800000 size=0x1000 writable=1 goal_level=1 pfn=0xfe800
```

`0xfe800000` 是这块 NVMe 的 BAR0 起始地址，不是普通内存。

追调用链：

```text
guest 访问 NVMe BAR GPA
    host KVM 缺页路径解析出 HPA = 0xfe800000（BAR0 起始地址）
        pkvm_hypercall(vm_mmu_map, gpa, hpa, size, ...)
            guest_mmu_map_leaf()
                __pkvm_host_donate_guest(hpa, ...)
                    do_donate()
                        host_initiate_donation()
                            find_mem_range(hpa, &range)
                                // BAR 地址不在 host RAM mem_range 里
                                // 失败，返回 addr not in mem_range
```

根因是：现有的 `__pkvm_host_donate_guest()` 是给普通内存页设计的，语义是"把 host RAM 捐给 pVM"。PCI BAR 地址不是内存，不应该走这条路。

解决方案是：在 hyp 侧判断 `[hpa, hpa + size)` 是否落在 boot-time manifest 记录的合法 BAR 范围内。如果命中了，就不走 donate，而是直接把这个 HPA 当 MMIO leaf 装入 Guest EPT。teardown 时也不走 undonate，只拆 Guest EPT leaf。

具体做了 4 件事：

**1. 扩展 boot-time manifest，记录每个设备的 memory BAR**

`pKVM-IA/arch/x86/kvm/vmx/pkvm/include/pkvm.h` 里扩展了 `struct pkvm_boot_ptdev_manifest_entry`，新增 `bars[]` 数组，每个 BAR 记录 `base` 和 `size`。`pKVM-IA/arch/x86/kvm/vmx/pkvm/pkvm_host.c` 的 `build_boot_ptdev_manifest()` 启动时遍历所有 PCI 设备，把每个设备的 memory BAR 全部存进去。

**2. 提供 HPA 是否命中 BAR 的统一 helper**

`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ptdev.c` 里新增了 `pkvm_boot_ptdev_bar_contains()`，公式很简单：

```text
命中条件：
    hpa >= bar_base
    hpa + size <= bar_base + bar_size
```

然后分别封装成两个对外函数：

- `pkvm_host_hpa_hits_boot_ptdev_bar(hpa, size)` — 在全量 boot manifest 里查，不管这个设备有没有 attach 给 VM
- `pkvm_vm_hpa_hits_attached_boot_ptdev_bar(kvm, hpa, size)` — 只在当前 VM 已经 attach 的设备里查

**3. `pkvm_vm_mmu_map()` 中做三段分流**

`pKVM-IA/arch/x86/kvm/pkvm/mmu.c` 里 `pkvm_vm_mmu_map()` 在正式建图前先判断：

```text
if (命中当前 VM attached BAR) {
    // direct BAR leaf：用 MMIO memory type 直接装入 Guest EPT
    // 不走 __pkvm_host_donate_guest()
    pgtable_map_leaf(...)
} else if (命中 host RAM mem_range) {
    // 普通 RAM：继续走 donate 路径
    __pkvm_host_donate_guest(...)
} else {
    // 既不是 BAR 也不是 RAM：直接拒绝，打印明确日志
    return -EPERM
}
```

同时 `guest_mmu_map_leaf()` 里也加了一次判断，命中 BAR 时直接跳到 `pgtable_map_leaf()`，不走 donate。

**4. teardown 时跳过 BAR leaf 的 undonate**

`guest_mmu_free_leaf()` 里，如果发现这个 leaf 的 `phys + size` 命中 BAR 范围，只拆 Guest EPT leaf，不调 `__pkvm_host_undonate_guest()`。

对应内核 commit：`501ca0cb907f`

改动文件：
- `pKVM-IA/arch/x86/kvm/pkvm/mmu.c` — 建图时分流，teardown 时跳过 undonate
- `pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ptdev.c` — 提供 BAR 范围命中判断的 helper
- `pKVM-IA/arch/x86/kvm/vmx/pkvm/include/pkvm.h` — 扩展 manifest 记录 memory BAR 的 base/size
- `pKVM-IA/arch/x86/kvm/vmx/pkvm/pkvm_host.c` — 启动期收集 BAR 数据

### 第三阶段：BOOT-012 修好了，但出现 BOOT-013

安装了包含 `501ca0cb907f` 的新内核后，protected pVM 又出现了新签名：

```text
[ERROR crosvm::crosvm::sys::linux::vcpu] vcpu hit unknown error: Bad address (os error 14)
[WARNING: CPU: 18 PID: 4255 at arch/x86/kvm/mmu/mmu.c:4775 kvm_tdp_page_fault+0x3f0/0x420]
```

追调用链：

```text
guest 访问 NVMe BAR GPA
    host KVM 缺页解析出 BAR HPA
        pkvm_page_fault()
            pkvm_hypercall(vm_mmu_map, gpa, hpa, size, ...)
                // B5-2 后命中 BAR 直接建 Guest EPT leaf（成功）
            pkvm_pin_page(vcpu->kvm, fault)
                kvm_pfn_to_refcounted_page(fault->pfn)
                    // BAR/MMIO PFN 不是普通 RAM，没有 refcounted struct page
                    return NULL
                WARN_ON_ONCE(!page)
                return -EFAULT
        KVM_RUN 返回 -EFAULT
```

根因是：host-high 的 `pkvm_page_fault()` 在建图成功后，对 protected VM 会无条件调 `pkvm_pin_page()` 把 host 页 pin 住，防止被回收或迁移。这对普通 RAM 是对的，但对 BAR/MMIO PFN 来说，`kvm_pfn_to_refcounted_page()` 返回 NULL，所以 `WARN_ON_ONCE` 触发并返回 `-EFAULT`。

解决方案是：在 `pkvm_page_fault()` 里对 `pkvm_pin_page()` 加一个保护，如果 `kvm_pfn_to_refcounted_page()` 返回 NULL，就跳过 pin 而不是报警失败。

对应内核 commit：`efba4f386b27`

改动文件：
- `pKVM-IA/arch/x86/kvm/mmu/mmu.c` — `pkvm_page_fault()` 中对 non-refcounted PFN 跳过 pin

### 验证结果

安装了包含 `efba4f386b27` 的内核后，重新跑同一条样例：

- protected pVM 成功启动到 `login:`，可以登录 `ubuntu`
- guest 内 `nvme0n1` 正常枚举
- 两轮 `dd` 都成功：`DD_RC=0`，`DD_BIG_RC=0`
- guest 内对 `pkvm_virt_mmio()` 打点，`dd` 窗口里 `direct_hit = 128`，`fallback_hit = 2`（2 条是 `sleep` 进程，不是 `dd`）
- host `dmesg` 不再出现：`Bad address`、`kvm_tdp_page_fault`、`pkvm_pin_page`、`host_initiate_donation: addr not in mem_range`、`vm_mmu_map failed`

## 暂时未解决的问题

### 问题 A：`pvmfw` GPA 路径还没排除 direct BAR HPA

当前 `pkvm_vm_mmu_map()` 已经允许命中 BAR 的 HPA 走 direct leaf 建图，但 `load_pvmfw()` / `gpa_range_overlaps_pvmfw()` 路径还没排除掉 direct BAR HPA。

这意味着如果 host 把某个 attached BAR 映到 `pvmfw` GPA，当前实现存在把 `pvmfw` 内容写入 BAR/MMIO 的风险。

本轮先记录，后续需要单独决定是：
- 拒绝 `direct_mmio && gpa_range_overlaps_pvmfw()`
- 还是把 `load_pvmfw()` 明确限制为 host RAM 路径

对应文档：`DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/01E-T10-B5-2-protected-pVM-Guest-EPT建图边界实现.md` 中的"待处理风险"一节。

### 问题 B：host `kvm_sev_es_mmio_write` 计数还有残余

修复后 host `kvm_sev_es_mmio_write` 里仍有写事件，但 guest 侧 `pkvm_virt_mmio()` trace 已经把 `dd` 任务本身钉在 `direct_hit`。

这说明这些 host write 事件不来源于这次 NVMe `dd` 的 MMIO 访问，而是来自 guest 生命周期中其他来源（比如 MSI-X 中断处理、固件访问等），需要后续单独分类。

对应原始记录：`DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/验证记录/t10-p8-host-trace-counts-guest-kprobe-window-0100-20260415-130256.log`

### 问题 C：本轮不检查 BAR 内 offset

当前验收标准只要求 `[hpa, hpa + size)` 完整落在 boot-time manifest 记录的某个 memory BAR 内，不检查 BAR 内 offset 是否和 guest GPA 对应。这留了一个小缺口：同一个 BAR 范围内 guest 访问不同 offset 都被认为合法。

本轮不处理，后续如果需要更严格的安全边界再单独评估。
