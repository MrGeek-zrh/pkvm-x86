# 2026 年 4 月 24 日 — T12 第一阶段实现与验证

## 今日目标

把 `B5-3 / T12` 从设计硬化推进到第一阶段内核实现：先做 device MMIO / assigned BAR 的最小 ownership transfer 闭环，再补源码级验证、测试用例设计和首轮运行证据。

## 过程记录

### 阶段一：先把 T12 设计从“想法”压成第一阶段边界

#### 现象

前一轮 `B5-3` 已经确认：`B5-2` 修的是 Guest EPT direct BAR 建图边界，不等价于 Host CPU 对 assigned BAR 的访问权已经被 pKVM 收口。

当前 x86 路径的问题仍然是：

```text
pkvm_attach_ptdev()
    ptdev->shadow_vm_handle = vm_handle
    ptdev->pgt = &vm->pgstate_pgt
    pkvm_shadow_vm_link_ptdev()
    pkvm_iommu_sync()
        -> 只切 DMA/IOMMU view
        -> 没有同步切 Host CPU 对 BAR 的访问权

handle_host_ept_violation()
    find_mem_range(gpa, &range)
        -> 非 RAM 地址
    pkvm_host_ept_map(..., HOST_EPT_DEF_MMIO_PROT)
        -> 普通 MMIO hole 可 lazy remap 回 Host EPT
```

#### 根因

之前如果只按“地址 revoke / denylist”做，很容易继续缺失这几件事：

- `ptdev` 上没有 BAR resource / owner / state 的真相源。
- Host EPT invalid PTE 没有 owner annotation，Host fault 不知道这个 BAR 已交给 pKVM 管。
- attach 失败、detach、teardown 恢复没有统一状态机。
- DMA view 和 guest allowlist 发布时间点没有和 BAR owner 切换排顺序。

#### 解决

今天把第一阶段边界写进总设计和实现规划：

- 总设计：`DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/01E-T12-B5-3-protected-pVM-device-MMIO-donate-机制总设计.md`
- 第一阶段实现规划：`DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/01E-T12-B5-3-device-MMIO-donate-第一阶段实现规划.md`
- 任务状态入口：`DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/01E-T12-B5-3-protected-pVM-assigned-BAR-Host-CPU-访问权收口.md`

第一阶段只承诺这条最小链路：

```text
attach protected ptdev
    snapshot / validate BAR resources
    annotate Host EPT invalid owner for assigned BAR
    switch ptdev DMA view to vm->pgstate_pgt
    publish guest MMIO allowlist only after owner/DMA state is ready

Host EPT fault on annotated BAR
    lookup invalid owner annotation
    owner == OWNER_ID_PTDEV_MMIO
    reject lazy remap

detach / rollback
    withdraw guest MMIO allowlist
    restore ptdev DMA view to Host EPT
    restore Host EPT idmap for touched BARs
```

不在第一阶段承诺完整 hotplug、migration、多设备共享 BAR、完整 reset 编排和通用 remove-path。

### 阶段三：实现 Host EPT owner annotation 和 deny-remap

#### 做了什么

先在 Host EPT 层补 MMIO owner annotation helper，再让 Host EPT fault 能识别这个 annotation：

- 内核 commit：`2713d30bcf26`（增加设备 MMIO 的 Host EPT 标注辅助函数）
- 内核 commit：`a1f7acdd7c19`（拒绝带标注的 Host BAR 重映射）
- 关键文件：`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ept.c`
- 关键文件：`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ept.h`
- 关键文件：`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/mem_protect.c`
- 关键文件：`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/mem_protect.h`

新的调用关系是：

```text
pkvm_host_ept_annotate_mmio_owner(hpa, size, OWNER_ID_PTDEV_MMIO)
    pkvm_init_invalid_leaf_owner(owner_id)
    pkvm_pgtable_annotate(&host_ept, hpa, size, annotation)
    pkvm_flush_host_ept()

handle_host_ept_violation()
    pkvm_host_ept_lookup_mmio_annotation_locked(gpa, &lookup)
    lookup.kind == PKVM_HOST_EPT_LOOKUP_ANNOTATED
    lookup.owner_id == OWNER_ID_PTDEV_MMIO
        -> pkvm: deny host BAR remap ...
        -> return -EPERM
```

#### 结果

第一阶段最核心的“Host 不应把 assigned BAR lazy remap 回来”有了专门分支。未标注的普通 MMIO hole 仍保留原有 lazy remap 行为，避免把普通 MMIO 一刀切禁掉。

### 阶段四：给 ptdev 增加 BAR authority 状态

#### 做了什么

接着把 BAR resource 和状态挂到 `ptdev` 上，而不是只靠零散地址判断：

- 内核 commit：`81b0c1207c80`（增加 ptdev BAR authority 状态）
- 关键文件：`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ptdev.h`
- 关键文件：`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ptdev.c`

新增的核心字段包括：

- `owner`
- `assignment_state`
- `managed_bar_mask`
- `touched_bar_mask`
- `bars[PCI_STD_NUM_BARS]`
- `dma_view_ready`
- `guest_contract_published`

状态推进变成：

```text
PKVM_PTDEV_DETACHED
    -> PKVM_PTDEV_ATTACHING
        -> PKVM_PTDEV_HOST_REVOKED
            -> PKVM_PTDEV_GUEST_ASSIGNED
                -> PKVM_PTDEV_RESTORING
                    -> PKVM_PTDEV_DETACHED
```

#### 结果

BAR 是否已经 revoke、是否可以发布给 guest、detach 时应该恢复哪些 BAR，不再只从调用点临时推断，而是落在 `struct pkvm_ptdev` 的状态里。

### 阶段五：拆分 metadata 缓存和 guest allowlist 发布

#### 现象

第一阶段不能在 userspace 提交 metadata 时就立刻把 allowlist 发布给 guest。因为那时候 Host BAR owner 和 DMA view 还未必完成切换。

#### 解决

- 内核 commit：`d4bf9376046a`（拆分 MMIO metadata 缓存与发布）
- 关键文件：`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ptdev.c`

新的顺序是：

```text
pkvm_set_ptdev_mmio_metadata()
    validate metadata against managed BAR resources
    cache metadata on ptdev
    do not publish guest allowlist yet

pkvm_publish_ptdev_mmio_contract_locked()
    check ptdev owner / state / dma_view_ready
    pkvm_update_vm_mmio_allowlist(vm, &ptdev->mmio_metadata)
    mark guest_contract_published
```

#### 结果

guest 只会在 BAR ownership 和 DMA view 都达到第一阶段条件后看到 direct BAR allowlist。这样避免“guest 已经拿到 MMIO contract，但 Host EPT / IOMMU 状态还没切好”的中间状态。

### 阶段六：接入 A/C/B attach 主线和 restore 路径

#### 做了什么

把实现顺序落进 `pkvm_attach_ptdev()` / `pkvm_detach_ptdev()`：

- 内核 commit：`380bc5421ef8`（接入 ptdev BAR donate attach 主线）
- 内核 commit：`fb569aabb2e6`（通过统一 helper 恢复 ptdev BAR）
- 内核 commit：`9f9531b5e36a`（补充 ptdev BAR donate 诊断日志）
- 关键文件：`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ptdev.c`

attach 现在按 A/C/B 的最小顺序推进：

```text
pkvm_attach_ptdev()
    pkvm_get_or_create_ptdev_checked()
    set shadow_vm_handle
    pkvm_revoke_ptdev_bars_locked()
        pkvm_prepare_ptdev_bar_resources_locked()
        pkvm_host_ept_annotate_mmio_owner(..., OWNER_ID_PTDEV_MMIO)
        bar->progress = PKVM_PTDEV_BAR_REVOKED
        owner = PKVM_PTDEV_OWNER_HYP
        assignment_state = PKVM_PTDEV_HOST_REVOKED
    ptdev->pgt = &vm->pgstate_pgt
    pkvm_shadow_vm_link_ptdev()
    pkvm_iommu_sync()
    dma_view_ready = true
    pkvm_publish_ptdev_mmio_contract_locked()
```

detach / rollback 现在走统一 restore helper：

```text
pkvm_detach_ptdev()
    pkvm_restore_ptdev_bars_locked(vm, ptdev, dma_unreachable_proven)
        pkvm_withdraw_ptdev_mmio_contract_locked()
        ptdev->pgt = pkvm_hyp->host_vm.ept
        pkvm_iommu_sync()
        pkvm_host_ept_restore_mmio_idmap(bar->hpa, bar->size, prot)
        clear touched BAR state
```

#### 结果

T12 第一阶段从“有 helper”推进到 attach / detach 主路径可走通的实现形态。诊断日志也补齐到最小可观测点：BAR revoke、BAR restore、Host BAR deny-remap。

### 阶段八：补 T12 第一阶段测试设计和回归 harness

#### 做了什么

为了后续不是手工散跑，新增了测试用例设计和一个最小回归工具：

- 测试设计：`DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/10-T12-第一阶段测试用例设计.md`
- 工具入口：`tests/pkvm-regress/pkvm-regress.py`
- 工具说明：`tests/pkvm-regress/README.md`

第一阶段把 case 分成三类：

- `scripted`：可以脚本化跑的正向/基础回归。
- `agent-runbook`：需要人工或 agent 按 runbook 判断的观测类 case。
- `fault-injection-required`：风险更高，需要显式确认的注入类 case。

工具当前能力包括：

- 列出 case registry。
- 生成 case plan。
- 扫描 forbidden signature。
- 生成验证记录骨架。
- `run-shell` 创建 artifact，并在风险动作前启动 live `dmesg` / `journalctl` collector。
- `recover-runs` 把遗留 `RUNNING` 标记为 `CRASHED_OR_INTERRUPTED`。

#### 结果

测试不再只是“跑一下 crosvm 看看”。后续如果 Host panic，至少有 `logs/host-dmesg-live.log`、`logs/host-journal-live.log`、`result.json`、`status.json` 可以作为问题记录和 GitHub issue 的证据入口。

### 阶段九：首轮运行验证暴露新签名

#### 现象

晚些时候用 `pKVM-IA` commit `9f9531b5e36a` 做了第一轮运行记录，入口是：

- 运行记录：`DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/验证记录/t12-phase1-run-20260424-160430.md`
- artifacts 根目录：`DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/验证记录/artifacts/`

三条关键结果是：

| Case | 结果 | 现象 |
|---|---|---|
| `T12-G2` | `COMPLETE` | protected pVM 无 VFIO 到达 login，并正常 poweroff |
| `T12-G1` | `COMPLETE` | normal VM + VFIO 到达 login，guest 内 `/dev/nvme0n1` direct I/O 返回 `DD_RC=0`，并正常 poweroff |
| `T12-A1` | `FAILED` | protected VM + VFIO 未到达 login；Host 日志出现 deny-remap 后触发 general protection fault |

`T12-A1` 的关键日志是：

```text
[Fri Apr 24 15:58:28 2026] pkvm: deny host BAR remap gpa=0xfe80200c owner_id=1048575 raw_pte=0xfffff000
[Fri Apr 24 15:58:28 2026] pkvm: handle host ept violation failed
[Fri Apr 24 15:58:28 2026] Oops: general protection fault, maybe for address 0xff402836c095900c: 0000 [#1] PREEMPT SMP NOPTI
[Fri Apr 24 15:58:28 2026] CPU: 6 UID: 0 PID: 3781 Comm: crosvm_vcpu0 Tainted: G S                 6.12.0-pkvm-ia #12
[Fri Apr 24 15:58:28 2026] RIP: 0010:raw_readl+0x0/0x10
```

原始日志：`DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/验证记录/artifacts/t12-20260424-155744-T12-A1/logs/host-dmesg-live.log`

#### 初步判断

这不是“deny-remap 没命中”。相反，T12 的 deny-remap 分支已经命中：

```text
handle_host_ept_violation()
    pkvm_host_ept_lookup_mmio_annotation_locked(gpa)
    owner_id == OWNER_ID_PTDEV_MMIO
    return -EPERM
        -> host 侧后续 raw_readl 访问 assigned BAR 地址
        -> general protection fault
```

也就是说第一阶段实现已经能阻止 Host lazy-remap assigned BAR，但 Host 当前调用方没有把这个 `-EPERM` 当成可恢复的 MMIO 访问失败处理，最后在 `raw_readl()` 路径上炸出来。

#### 结果

今天的最终状态不是“运行验证通过”，而是：

- T12 第一阶段源码实现已形成最小闭环。
- 基础负载 `T12-G2` / `T12-G1` 能跑通。
- protected VFIO 正向 case `T12-A1` 暴露新 blocker：deny-remap 后 Host 仍有 `raw_readl()` 路径触发 general protection fault。
- 这条新签名需要后续按独立 Bug issue / 问题记录处理，不能继续塞回 `B5-2` 或把 `T12` 直接标成完成。
