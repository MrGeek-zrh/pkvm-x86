## 过程记录

### 阶段一：确认 B5-2 不是 B5-3 的完成证明

#### 现象

`B5-2` 已经解决的是 protected pVM 首次访问 passthrough BAR 时，Guest EPT 能否正确建 direct BAR leaf 的问题。这个结论不自动覆盖 Host CPU 后续是否还能把 assigned BAR 重新映射回来。

当时重新检查的 Host EPT 缺页路径是：

```text
handle_host_ept_violation()
    find_mem_range(gpa, &range)
        -> 非 RAM 地址
    pkvm_host_ept_map(..., HOST_EPT_DEF_MMIO_PROT)
        -> 普通 MMIO hole 仍可能被 lazy remap 回 Host EPT
```

也就是说，如果 attach 阶段只是简单 unmap assigned BAR，但 Host EPT invalid leaf 上没有 owner annotation，Host 后续 fault 仍然可能重新把 BAR 映射回 Host。

#### 根因

当前 `pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/ptdev.c` 里的 `pkvm_attach_ptdev()` / `pkvm_detach_ptdev()` 主要切的是 DMA / IOMMU 视角：

```text
pkvm_attach_ptdev()
    pkvm_get_or_create_ptdev_checked()
    ptdev->shadow_vm_handle = vm_handle
    ptdev->pgt = &vm->pgstate_pgt
    pkvm_shadow_vm_link_ptdev()
    pkvm_iommu_sync()

pkvm_detach_ptdev()
    ptdev->shadow_vm_handle = 0
    ptdev->dma_blocked = false
    clear mmio_metadata
    ptdev->pgt = pkvm_hyp->host_vm.ept
```

这条路径没有把 Host CPU 对 BAR 的访问权纳入同一个状态机。上一轮本地临时 patch 想直接在 attach / fault / detach 三处按 BAR 地址做 revoke / deny / restore，但缺少 `ptdev` 内部 authoritative owner state、Host EPT invalid owner annotation、失败回滚和 teardown 语义，所以今天没有继续沿用那版 patch。

#### 结果

`B5-2` 的口径被收窄为“Guest EPT 首次建图边界已收口”。Host CPU 对 assigned BAR 的访问权单独交给 `B5-3 / T12` 跟踪，不再混在 `B5-2` 的完成结论里。

#### 做了什么

补了一份 ARM 参考实现总结和一份 x86 对齐草案，核心是把设备 MMIO / BAR 看成设备资源的 ownership transfer，而不是普通 RAM donation：

- ARM 参考总结：`DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/参考实现/ARM-pKVM-设备BAR-MMIO-donate机制总结.md`

- T12 收口任务：`DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/01E-T12-B5-3-protected-pVM-assigned-BAR-Host-CPU-访问权收口.md`

#### 收敛出的结论

今天先把方向定成：

```text
Host
    -> Hyp owns assigned device BAR / MMIO resource
        -> Host EPT invalid leaf carries owner annotation
        -> Host fault sees non-Host owner and must not lazy-remap
        -> Guest receives controlled MMIO contract / allowlist
```

这里的重点不是“找一个地址 denylist”，而是让 `ptdev` BAR resource、owner、state 变成 pKVM/hyp 侧的真相源。
