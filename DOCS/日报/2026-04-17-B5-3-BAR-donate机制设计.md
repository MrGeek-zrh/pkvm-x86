# 2026 年 4 月 17 日 — B5-3 BAR donate 机制设计

## 今日目标

讨论并收敛 `B5-3 / T12` 的解决方案：protected pVM 透传设备后，Host CPU 对 assigned BAR 的访问权如何收口，以及 BAR / MMIO 不应继续套用普通 RAM donation 语义，而应设计成设备 BAR / MMIO 专用的 ownership transfer。

## 过程记录

### 阶段一：先把 B5-2 和 B5-3 的边界拆开

#### 现象

`B5-2` 已经解决的是 Guest EPT 首次建图边界：

- 命中当前 VM 已 attach boot BAR 的 HPA 时，允许 direct BAR leaf 建图
- 未命中 BAR 且也不在 host RAM `mem_range` 内时，提前 reject
- BAR leaf teardown 时不再走 `__pkvm_host_undonate_guest()`

但这不等价于 Host CPU 后续不能继续直接读写 assigned BAR。当前 `handle_host_ept_violation()` 对普通 MMIO hole 仍有 lazy remap 行为：

```text
handle_host_ept_violation()
    find_mem_range(gpa, &range)
        -> 非 RAM 地址
    pkvm_host_ept_map(..., HOST_EPT_DEF_MMIO_PROT)
```

如果 assigned BAR 只是被简单 unmap，而 Host EPT invalid leaf 没有 owner annotation，后续 Host fault 仍可能把它 map 回 Host。

#### 根因

当前 `pkvm_attach_ptdev()` / `pkvm_detach_ptdev()` 主要切的是 DMA / IOMMU 视角，还没有把 Host CPU 对 BAR 的访问权纳入同一个状态机：

```text
pkvm_attach_ptdev()
    pkvm_get_or_create_ptdev_checked()
    ptdev->shadow_vm_handle = vm_handle
    ptdev->pgt = &vm->pgstate_pgt
    pkvm_shadow_vm_link_ptdev()
    pkvm_iommu_sync()

pkvm_detach_ptdev()
    ptdev->shadow_vm_handle = 0
    ptdev->dma_blocked = false
    clear mmio_metadata
    ptdev->pgt = pkvm_hyp->host_vm.ept
    pkvm_shadow_vm_unlink_ptdev()
    pkvm_iommu_sync()
```

这说明当前已经有 `ptdev`、boot manifest 和 IOMMU / DMA mirror 基础，但还没有 Host BAR ownership 这层状态。

#### 解决方案

把这条缺口从 `B5-2` 里拆出来，单独作为 `B5-3 / T12` 处理：

- `B5-2`：Guest EPT 首次建图边界
- `B5-3 / T12`：Host CPU 对 assigned BAR 的访问权收口

对应文档入口：

- `DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/01E-T12-B5-3-protected-pVM-assigned-BAR-Host-CPU-访问权收口.md`

#### 结果

后续讨论不再把“BAR HPA 能不能给 guest 建图”和“Host CPU 能不能继续通过 Host EPT 访问 BAR”混成一个问题。当前主线前移到 `T12 / pkvm-x86#34`。

### 阶段二：否定简单的地址 revoke / deny-remap patch

#### 现象

上一轮曾经考虑过一个直接方案：

- attach 时对 BAR 做 `pkvm_host_ept_unmap()`
- Host EPT fault 时按 attached BAR 地址 deny-remap
- detach 时用 `pkvm_host_ept_map()` 恢复 BAR

这个方案能覆盖一部分现象，但不像一个完整的 BAR donate 机制。

#### 根因

这版 patch 的问题不是“Host BAR 不需要隔离”，而是它缺少三件关键东西：

- hyp 内部没有 BAR owner authoritative state
- Host EPT invalid leaf 没有记录“这段 MMIO 已不归 Host”
- attach 失败、remove-path、teardown rollback 没有 generation 语义

也就是说，地址 deny-remap 只能回答“这次 fault 要不要拒绝”，不能回答“这段 BAR 现在归谁、走到 assignment 的哪一步、失败后如何恢复”。

#### 解决方案

当前决定丢弃这版未提交的本地 patch，不继续沿“地址特判”往前写，改成先做 BAR ownership 状态机设计。

对应设计草案：

- `DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/01E-T12-B5-3-Host-BAR隔离-ARM对齐设计草案.md`

#### 结果

`T12` 的方向从“fault path 上拦一次地址”调整为“让 `ptdev` 承载 BAR resource / owner / lifecycle state”。

### 阶段三：对齐 ARM pKVM 的设备 BAR / MMIO donate 机制

#### 现象

如果继续把设备 BAR 当普通 RAM 来 donate，会马上遇到当前 x86 已经暴露过的问题：

```text
host_initiate_donation()
    find_mem_range(addr, &range)
        -> 只接受普通 RAM
    hyp_page_count(__hyp_va(cur))
        -> 依赖 hyp vmemmap / struct hyp_page 元数据
```

设备 BAR / MMIO 不在普通 RAM `mem_range` 里，也不适合走 `hyp_page_count(__hyp_va(cur))` 这条普通页语义。

#### 根因

ARM pKVM 对设备 BAR / MMIO 的处理不是简单的 `Host -> Guest` 普通 RAM donate，而是设备资源专用路径：

```text
Host
    --(pkvm_device_hyp_assign_mmio)-->
Hyp
    --(pkvm_host_map_guest_mmio / pkvm_hyp_donate_guest)-->
Guest
    --(teardown / reclaim)-->
Host
```

这里最关键的是先让 Hyp 成为中间 owner。Hyp 先拿到一个“Host 和 Guest 都暂时不能碰设备”的窗口，后续才能做 reset、DMA block、IOMMU group assign 和失败回滚。

#### 解决方案

整理 ARM 参考实现后，把 BAR / MMIO donate 机制总结成四个结论：

1. 设备 MMIO 走的是 `Host -> Hyp -> Guest`，不是普通 RAM 的 `Host -> Guest`
2. `pkvm_device_hyp_assign_mmio()` 先用资源级匹配确认 MMIO 属于已注册 device resource
3. `___pkvm_host_donate_hyp_prot(..., accept_mmio=true, PAGE_HYP_DEVICE)` 表明这条路径明确接受 MMIO，并按 device/MMIO 语义给 Hyp
4. Host fault 不会自动 remap，是因为 host stage-2 invalid leaf 里保留 owner annotation，而不是因为有一张临时地址 denylist

对应 ARM 侧关键链路：

```text
pkvm_device_hyp_assign_mmio()
    pkvm_get_device(phys, size)
    ___pkvm_host_donate_hyp_prot(pfn, nr_pages, true, PAGE_HYP_DEVICE)
        __pkvm_host_donate_hyp_locked()
            host_stage2_set_owner_locked(phys, size, PKVM_ID_HYP)
                __host_stage2_set_owner_locked()
                    kvm_pgtable_stage2_annotate(...)

Host data abort
    handle_host_mem_abort()
        host_stage2_idmap(addr)
            host_stage2_adjust_range(addr, &range)
                invalid PTE has owner annotation
                    return -EPERM
        host_inject_abort()

pkvm_host_map_guest_mmio()
    pkvm_get_device_by_addr()
    __pkvm_group_assign(dev->group_id, vm)
        __pkvm_device_assign()
            hyp_check_range_owned()
            pkvm_device_reset(dev, true)
            kvm_iommu_dev_block_dma(..., host_to_guest=true)
            dev->ctxt = vm
    __pkvm_install_guest_mmio()
        __pkvm_remove_ioguard_page()
        pkvm_hyp_donate_guest()
```

对应文档：

- `DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/参考实现/ARM-pKVM-设备BAR-MMIO-donate机制总结.md`

#### 结果

当前得到的设计判断是：x86 侧不能把 BAR/MMIO 强塞进普通 RAM donation 主链，而应补一条 MMIO 专用的 `Host -> Hyp` ownership transfer，再由 Hyp 按设备 assignment 状态把 BAR 暴露给 Guest。

### 阶段四：把 ARM 结论映射回 x86 的 T12 方案

#### 现象

x86 现在已有这些基础：

- boot manifest 里已经有 boot-known 设备与 BAR 区间
- `struct pkvm_ptdev` 已经承载 BDF、PASID、DID、`pgt`、`shadow_vm_handle`、`dma_blocked`、`mmio_metadata`
- Host EPT 普通 RAM donation 已经有 invalid owner annotation 机制

但这些还没有合成 BAR ownership 状态机。

#### 根因

现有普通 RAM donation 链路不能直接复用到 BAR，因为：

- `host_initiate_donation()` 依赖 `find_mem_range()`
- `host_initiate_donation()` 依赖 `hyp_page_count(__hyp_va(cur))`
- BAR / MMIO 是设备资源，不是普通 host RAM page

同时，单独改 `handle_host_ept_violation()` 也不够，因为 attach 阶段已有的 Host BAR 映射不会被自动回收。

#### 解决方案

当前推荐把 `T12` 第一阶段设计成：

1. 在 `ptdev` 下维护 BAR resource snapshot：
  - `base`
  - `size`
  - `flags`
  - `owner`
  - `state`
  - `generation`
2. 增加 MMIO 专用 `Host -> Hyp` ownership transfer：
  - 不复用普通 RAM 的 `host_initiate_donation()`
  - 不要求 BAR 落在 `find_mem_range()`
  - 不走 `hyp_page_count(__hyp_va())`
  - 只对 Host EPT 写 invalid owner annotation，并按 device/MMIO 属性维护状态
3. 修改 Host EPT fault：
  - invalid PTE 带 owner annotation 且 owner 不是 Host 时，拒绝 lazy remap
  - 未标注的普通 MMIO hole 继续保持现有 remap 行为
4. attach / detach 改为状态机：
  - attach：固化 BAR resource -> Host->Hyp revoke -> 切 DMA/IOMMU view -> 发布 guest allowlist
  - detach：quiesce/block DMA -> 清 guest allowlist -> restore Host owner -> 清 BAR state

#### 结果

`T12` 的实现边界已经从“地址匹配 + fault 特判”收敛成：

- `ptdev` BAR resource / owner / state
- MMIO 专用 Host -> Hyp ownership transfer
- Host EPT invalid owner annotation
- Host fault deny-remap
- attach / detach / rollback 状态机

### 阶段五：确认 T12 和 T4 的关系

#### 现象

`T4` 也涉及 teardown 前的设备 DMA 生命周期，容易和 `T12` 的 BAR ownership 混在一起。

#### 根因

两者相关，但解决的问题不同：

- `T4` 解决的是 guest 页回到 Host 前，设备 DMA 通路必须先被切断
- `T12` 解决的是 Host CPU 是否还能通过 BAR / Host EPT 继续访问设备控制面

#### 解决方案

当前口径是：

- 不让 `T12 / BAR ownership` 反向阻塞 `T4` 第一版
- `T4` 第一版继续沿用前置 `quiesce / block DMA`
- `T12` 独立推进 BAR resource / owner / state
- 待 `T12` 完成后，再评估是否基于同一套 `ptdev owner/state` 优化 `T4` 的 teardown 编排

对应文档：

- `DOCS/需求/分析当前pKVM-IA对设备透传的支持情况/实施跟踪/04-P0-VM销毁前quiesce-ptdev-DMA.md`

#### 结果

`T4` 和 `T12` 的边界已经拆开：`T4` 不再是当前 BAR donate 机制设计的前置 blocker，`T12` 也不替代 `T4` 的 DMA quiesce。

## 今日未完成

- `T12` 还停在设计阶段，`ptdev` 的 BAR `owner / state / generation` 还没有进 `pKVM-IA` 代码。
- Host EPT invalid owner annotation 的读取 helper 还没定稿。
- MMIO 专用 `Host -> Hyp` ownership transfer 还没有写成最小 patch。
- attach 失败、detach、remove-path 的 rollback 还只是设计项，后面还要和 `T4 / T6` 对齐。
- `owner` 第一阶段到底保持 `HYP-with-guest-mapping`，还是直接引入更明确的 `GUEST` owner，还需要继续确认。
