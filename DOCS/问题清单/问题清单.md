# 问题清单（Known Issues）

## 启动类

### [BOOT-001] 启用 pKVM 后 early boot panic（jump_label / return thunk）

**现象**

- `Unpatched return thunk in use. This should not happen!`
- `jump_label: Fatal kernel bug, unexpected op at restore_fpregs_from_fpstate__pkvm+0x13 ... (eb 41 ... != 66 90 ...) size:2 type:1`
- `kernel BUG at arch/x86/kernel/jump_label.c:73!`

**原始日志（节选）**

```text
[    1.153835] Unpatched return thunk in use. This should not happen!
[    1.155312] WARNING: CPU: 0 PID: 1 at arch/x86/kernel/cpu/bugs.c:3225 __warn_thunk+0x40/0x50
...
[    1.194946]  warn_thunk_thunk+0x16/0x30
[    1.195923]  vmx_pkvm_init+0xbc/0xf00
...
[    1.207286] jump_label: Fatal kernel bug, unexpected op at restore_fpregs_from_fpstate__pkvm+0x13/0x90 [00000000ca919d0f] (eb 41 48 23 35 != 66 90 0f 1f 00)) size:2 type:1
[    1.211941] kernel BUG at arch/x86/kernel/jump_label.c:73!
[    1.213267] Oops: invalid opcode: 0000 [#1] PREEMPT SMP NOPTI
...
[    1.213976] RIP: 0010:__jump_label_patch+0x129/0x130
...
[    1.302571] Kernel panic - not syncing: Attempted to kill init! exitcode=0x0000000b
```

**触发路径（常见回溯）**  
`vmx_pkvm_init -> static_key_enable -> jump_label_update -> __jump_label_patch`

**根因（简述）**  
`arch/x86/kvm/vmx/pkvm/hyp` 下的 `*.pkvm.o` 使用自定义构建规则生成，未启用 objtool 时，x86 的 jump_label hack 位点不会被预处理为期望的 NOP/元数据；运行时 patch 校验读到 `eb xx` 而不是 `66 90`，因此按“kernel text 异常”触发 `BUG()`。

**解决方案（推荐）**

- 让 `*.pkvm.o` 也启用 objtool：在“你正在使用的内核源码树”里对应的 `arch/x86/kvm/vmx/pkvm/hyp/Makefile`，为 `$(obj)/%.pkvm.o` 增加 `private objtool-enabled := y`（例如：`pKVM-IA/.../hyp/Makefile`、`pvVMCS-POC-v6.12/.../hyp/Makefile`）。

**验证要点**

- 重新编译后，`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/pkvm.o` 中 `restore_fpregs_from_fpstate__pkvm+0x13` 附近应为 `66 90`（NOP），不应是 `eb xx`（短跳）。

**触发条件（复现场景）**

- Host 内核启用 pKVM：`kvm-intel.pkvm=1`
- Host 开启 Intel IOMMU：`intel_iommu=on`（`intel_iommu=sm_on` / `sm_off`与本问题无关）
- QEMU 暴露 vIOMMU：如 `-machine q35` + `-device intel-iommu,...`
- 内核配置启用 pvIOMMU：`CONFIG_PKVM_INTEL_PVIOMMU=y`

**根因（简述）**

- host 的 Intel VT-d 驱动写 `RTADDR` 并在 `GCMD` 里发出 `SRTP`，随后轮询 `GSTS.RTPS` 等待置位。
- 在 pKVM-IA 中，上述 IOMMU MMIO 会被 hypervisor 拦截，`SRTP` 触发 `handle_gcmd_srtp()` -> `activate_iommu()`。
- 该路径需要初始化 QI（Queued Invalidation）并分配 `qi->desc`（8KB，order=1）。但当 `CONFIG_PKVM_INTEL_PVIOMMU=y` 时：
  - `divide_memory_pool()` 中为 IOMMU 预留的 `iommu_mem_base` 不会分配（`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/init_finalise.c` 内 `#ifndef CONFIG_PKVM_INTEL_PVIOMMU` 分支）。
  - `pkvm_init_iommu()` 中也不会初始化 `iommu_pool`（`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/iommu.c` 内同样的 `#ifndef` 分支）。
  - 但 `initialize_qi()` 仍走 `iommu_zalloc_pages()` 从 `iommu_pool` 分配内存，导致 `hyp_alloc_pages()` 直接 `-ENOMEM`。
- 结果：`activate_iommu()` 失败 -> pKVM 不会置位虚拟 `GSTS.RTPS` -> host 侧一直等不到 `RTPS` -> `IOMMU_WAIT_OP()` 超时后 panic。

**解决方案**

- 方案 1（已验证可启动，推荐先用）：关闭 pvIOMMU，使用 shadow IOMMU 路线  
  - 配置：将 `CONFIG_PKVM_INTEL_PVIOMMU=n` 重新编译安装内核。
- 方案 2（需要代码支持）：保持 pvIOMMU，但补齐“host 动态分配并 donate 给 pKVM”的内存来源  
  - 目标：让 `initialize_qi()` / 相关结构不再依赖 `iommu_pool` 预留内存（或在 pvIOMMU 模式下提供等价的 pool 初始化）。

**验证要点**

- 启动日志不再出现 `handle_gcmd_srtp ... err=-12` / `IOMMU_WAIT_OP timeout` / `DMAR hardware is malfunctioning`。

## 构建/镜像制作类

### [IMG-001] 宿主机 nbd 模块无法加载（Exec format error），导致 create-guestimg/qemu-nbd 失败

**现象**

- 宿主机执行 `sudo modprobe nbd max_part=8`：
  - `modprobe: ERROR: could not insert 'nbd': Exec format error`
- 在 `scripts/create-guestimg.sh` / `scripts/chroot-utils.sh` 创建 qcow2 阶段：
  - `modprobe: ERROR: could not insert 'nbd': Exec format error`
  - `qemu-nbd: Cannot open /dev/nbd0: No such file or directory`

**影响**

- `scripts/chroot-utils.sh` 的 `sysroot_create_image_file()` 依赖 `/dev/nbd0` 将 qcow2 连接成块设备并分区/格式化。
- 因此该问题会阻断 guest qcow2 的自动生成流程（包括 Docker 容器内执行也一样）。

**线索**

- `dmesg` 可能出现：
  - `module (missing .modinfo section or name field): Only one .gnu.linkonce.this_module section must exist.`
- 运行内核示例：`6.12.0-pkvm-ia`
- 检查 `nbd.ko` 示例：
  - 路径：`/lib/modules/6.12.0-pkvm-ia/kernel/drivers/block/nbd.ko`
  - `modinfo -F vermagic` 看起来匹配，但 `modinfo -F name` 为空（缺失 `name=` 字段）

**根因（已验证）**

- 实际安装到 `/lib/modules/<uname -r>/` 的 `*.ko` 里，存在“未正确链接进 `*.mod.o`”的情况，导致：
  - `modinfo -F name <mod>` 为空（`.modinfo` 里缺失 `name=<mod>`）
  - `nm -n <mod>.ko | grep __this_module` 显示 `U __this_module`（未定义符号）
  - `modprobe` 因模块格式不完整而报 `Exec format error`
- 在内核源码树的构建产物里，往往还能看到对应的 `*.mod.o` 为 **0 字节**（多见于编译/打包过程被中断或异常终止后留下的“空目标文件”）；后续增量构建可能不会自动重建这些空文件，从而把“坏模块”一路打进 .deb 并安装到系统里。

**处理办法（推荐/已验证）**

- 1. 先确认是不是这个问题（以 `nbd` 为例）：

```bash
uname -r
modinfo -F name nbd            # 期望输出: nbd（如果为空，基本就中招）
nm -n /lib/modules/$(uname -r)/kernel/drivers/block/nbd.ko | grep __this_module
```

- 1. 在内核源码树/构建输出里排查是否存在 0 字节的 `*.mod.o`（如果你用 out-of-tree 构建，请在 `O=<builddir>` 下执行同样检查）：

```bash
cd /path/to/pKVM-IA
find . -name '*.mod.o' -size 0 -print | head
```

- 1. 修复方式：清理 0 字节 `*.mod.o` 并重新构建/安装内核：

```bash
cd /path/to/pKVM-IA
find . -name '*.mod.o' -size 0 -delete
make -j"$(nproc)" modules
DOCS/pKVM-IA-docs/build-host-kernel.sh
sudo dpkg -i /home/mrgeek/pkvm-x86/linux-image-*-pkvm-ia_*.deb /home/mrgeek/pkvm-x86/linux-headers-*-pkvm-ia_*.deb
```

安装后甚至不需要重启，理论上即可解决问题。

**验证要点**

- `modinfo -F name nbd` 输出为 `nbd`
- `modprobe nbd max_part=8` 成功，且`ls /dev/nbd0`应该是存在的

### [RUN-001] pKVM Host 已启用，但使用 crosvm 启动 Protected Guest 时 dmesg 报 “Failed to set cpuid pages for pkvm vcpu”

**现象**

- Host 已成功进入 pKVM 模式（启动日志可见 `pkvm_host_deprivilege_cpus: all cpus are in guest mode!` 等）。
- 启动 Protected Guest（crosvm `--protected-vm-without-firmware`）后，Host `dmesg` 出现：

```text
[41529.589423] pkvm: xfd_enable_feature insufficient fpstate: cur=4096 need=10752 xfd_event=0x40000 cur_xfeatures=0x202e7
[41529.589981] pkvm: xfd_enable_feature insufficient fpstate: cur=4096 need=10752 xfd_event=0x40000 cur_xfeatures=0x202e7
[41529.590351] pkvm: vcpu_after_set_cpuid kvm_set_cpuid failed ret=-12 gpa=0x4284b7000 nent=57
[41529.591198] pkvm: vcpu_after_set_cpuid kvm_set_cpuid failed ret=-12 gpa=0x1e6c70000 nent=57
[41529.592215] kvm [8155]: Failed to set cpuid pages for pkvm vcpu (vcpu_id=0 nent=55 size=2200 entries_pa=0x00000004284b7000 ret_pa=0x00000004284b7000)
[41529.592841] kvm [8156]: Failed to set cpuid pages for pkvm vcpu (vcpu_id=1 nent=55 size=2200 entries_pa=0x00000001e6c70000 ret_pa=0x00000001e6c70000)
```

**复现命令**

```bash
sudo SETUP_NET=0 \
  CROSVM=/home/mrgeek/pkvm-x86/crosvm/target/debug/crosvm \
  IMAGE=/home/mrgeek/pkvm-x86/images/guest/ubuntuguest.qcow2 \
  KERNEL=/home/mrgeek/pkvm-x86/images/guest/bzImage \
  /home/mrgeek/pkvm-x86/scripts/run-crosvm.sh
```

**对比**

- 去掉 `--protected-vm-without-firmware` 后，普通 KVM guest 可正常启动（说明镜像/bzImage/基础 KVM 路径正常）。

**定位结论（2026-02-05）**

- 该错误不是 “Host 分配 cpuid pages 失败”，而是 **pKVM hyp/kvm-low 侧 `kvm_set_cpuid()` 返回了 `-12`（`-ENOMEM`）**，导致 hypercall `vcpu_after_set_cpuid` 失败并按约定“原样返回 gpa”，Host 侧据此打印 `Failed to set cpuid pages for pkvm vcpu` 并释放新分配的 buffer。
- 从日志可见 Host 侧 `nent=55`，但 hyp 侧错误日志里 `nent=57`，说明 hyp 侧在 `pkvm_enforce_cpuid()` 阶段可能插入/补齐了额外的 CPUID entries（安全强制），随后在 `kvm_set_cpuid()` 阶段失败。
- 结合本仓库代码，`kvm_set_cpuid()` 返回 `-ENOMEM` 的一个高概率原因是：**guest CPUID 暴露了 dynamic xfeatures/XFD 相关能力，但 pVM 的 fpstate size 不足**。在 hyp 侧 `pKVM-IA/arch/x86/kvm/pkvm/fpu/xstate.c::__xfd_enable_feature()` 中，如果计算出的所需 fpstate 大小 `ksize` 大于当前 `fps->size`，会直接返回 `-ENOMEM`。

**错误路径（函数调用链，按函数名缩进）**

```text
userspace (crosvm/qemu)
    ioctl(KVM_SET_CPUID2)

kvm-high (Host kernel)
    kvm_vcpu_ioctl_set_cpuid2(...)
        kvm_set_cpuid(vcpu, e2, nent=55)
            kvm_vcpu_after_set_cpuid(vcpu)
                kvm_x86_call(vcpu_after_set_cpuid)(vcpu)
                    pkvm_vcpu_after_set_cpuid(vcpu)
                        pkvm_hypercall(vcpu_after_set_cpuid, vcpu, entries_pa, nent=55)
                            (returns entries_pa on failure)
                        kvm_err("Failed to set cpuid pages for pkvm vcpu ...")

pKVM (hypervisor / kvm-low)
    handle_vmcall(vcpu)
        handle_kvm_call(fn=__pkvm__vcpu_after_set_cpuid, p1=shared_vcpu, p2=gpa, p3=nent=55, ...)
            pkvm_vcpu_handle_kvm_call(fn, shared_vcpu, p2, p3)
                pkvm_vcpu_after_set_cpuid(pkvm_vcpu, gpa, new_nent=55)
                    donate_host_memory(gpa, aligned_size)
                    pkvm_enforce_cpuid(new_entries, &new_nent)
                        (may append/modify entries, observed new_nent=57)
                    kvm_set_cpuid(vcpu, new_entries, new_nent=57)
                        kvm_check_cpuid(vcpu, entries, nent)
                            fpu_enable_guest_xfd_features(&vcpu->arch.guest_fpu, xfeatures)
                                __xfd_enable_feature(xfd_event=0x40000, guest_fpu)
                                    (fpstate too small: cur=4096 need=10752)
                                    return -ENOMEM
                        return -ENOMEM
                    return gpa   (hypercall failure: return original gpa)
```

**下一步建议**

- 已确认根因是 `xfd_enable_feature` 检测到 **fpstate size 不足**（例如 `cur=4096 need=10752 xfd_event=0x40000`），导致 hyp 侧 `kvm_set_cpuid()` 返回 `-ENOMEM`，从而触发 host 侧 `Failed to set cpuid pages for pkvm vcpu`。
- 后续排查/修复方向：
  1. 检查并修复 Host 侧 `pKVM-IA/arch/x86/kvm/vmx/pkvm_high.c:pkvm_vcpu_after_set_cpuid()` 的 fpstate 扩容链路（`vcpu_add_fpstate` hypercall）：是否触发、donate 的 size 是否至少覆盖 hyp 侧所需 `need`（需页对齐，例如 `need=10752` 至少应扩到 `12288`）。
  2. 若短期需要绕过：在 pVM 的 CPUID 中屏蔽触发 `xfd_event=0x40000` 的 dynamic xfeatures（避免走 XFD 扩容检查路径），待 fpstate 扩容链路完善后再恢复。

**绕过验证（2026-02-06）**

- 在 Host 内核启动参数增加 `clearcpuid=amx_tile` 后，pVM 可启动成功，说明 RUN-001 的核心阻塞点确实与 `xfd_event=0x40000`（疑似 AMX/XTILEDATA）触发的 fpstate size 检查有关。
