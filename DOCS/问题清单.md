# 问题清单（Known Issues）

本文件用于记录“会影响构建/启动/功能验证”的已知问题、现象与处理办法，便于复现与排查。

## 启动类

### [BOOT-001] 启用 pKVM 后 early boot panic（jump_label / return thunk）

**现象**

- `Unpatched return thunk in use. This should not happen!`
- `jump_label: Fatal kernel bug, unexpected op at restore_fpregs_from_fpstate__pkvm+0x13 ... (eb 41 ... != 66 90 ...) size:2 type:1`
- `kernel BUG at arch/x86/kernel/jump_label.c:73!`

**原始日志（节选）**

```text
[    1.153835] Unpatched return thunk in use. This should not happen!
[    1.155312] WARNING: CPU: 0 PID: 1 at arch/x86/kernel/cpu/bugs.c:3225 __warn_thunk+0x40/0x50
...
[    1.194946]  warn_thunk_thunk+0x16/0x30
[    1.195923]  vmx_pkvm_init+0xbc/0xf00
...
[    1.207286] jump_label: Fatal kernel bug, unexpected op at restore_fpregs_from_fpstate__pkvm+0x13/0x90 [00000000ca919d0f] (eb 41 48 23 35 != 66 90 0f 1f 00)) size:2 type:1
[    1.211941] kernel BUG at arch/x86/kernel/jump_label.c:73!
[    1.213267] Oops: invalid opcode: 0000 [#1] PREEMPT SMP NOPTI
...
[    1.213976] RIP: 0010:__jump_label_patch+0x129/0x130
...
[    1.302571] Kernel panic - not syncing: Attempted to kill init! exitcode=0x0000000b
```

**触发路径（常见回溯）**  
`vmx_pkvm_init -> static_key_enable -> jump_label_update -> __jump_label_patch`

**根因（简述）**  
`arch/x86/kvm/vmx/pkvm/hyp` 下的 `*.pkvm.o` 使用自定义构建规则生成，未启用 objtool 时，x86 的 jump_label hack 位点不会被预处理为期望的 NOP/元数据；运行时 patch 校验读到 `eb xx` 而不是 `66 90`，因此按“kernel text 异常”触发 `BUG()`。

**解决方案（推荐）**

- 让 `*.pkvm.o` 也启用 objtool：在 `pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/Makefile` 为 `$(obj)/%.pkvm.o` 增加 `private objtool-enabled := y`。

**验证要点**

- 重新编译后，`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/pkvm.o` 中 `restore_fpregs_from_fpstate__pkvm+0x13` 附近应为 `66 90`（NOP），不应是 `eb xx`（短跳）。

### [BOOT-002] 启用 pKVM + pvIOMMU 时，IOMMU 初始化 SRTP 超时导致 panic（DMAR hardware is malfunctioning）

**现象**

- 启动早期在 `intel_iommu_init()` 阶段 panic：`Kernel panic - not syncing: DMAR hardware is malfunctioning`
- 日志通常能看到：
  - `pkvm: iommu0: SRTP request ...`
  - `pkvm: handle_gcmd_srtp: iommu0 failed to activate(err=-12)`
  - 随后 host 侧 `IOMMU_WAIT_OP timeout`（等待 `GSTS.RTPS` 置位超时）

**原始日志（节选）**


**触发条件（复现场景）**

- Host 内核启用 pKVM：`kvm-intel.pkvm=1`
- Host 开启 Intel IOMMU：`intel_iommu=on`（`intel_iommu=sm_on` / `sm_off`与本问题无关）
- QEMU 暴露 vIOMMU：如 `-machine q35` + `-device intel-iommu,...`
- 内核配置启用 pvIOMMU：`CONFIG_PKVM_INTEL_PVIOMMU=y`

**根因（简述）**

- host 的 Intel VT-d 驱动写 `RTADDR` 并在 `GCMD` 里发出 `SRTP`，随后轮询 `GSTS.RTPS` 等待置位。
- 在 pKVM-IA 中，上述 IOMMU MMIO 会被 hypervisor 拦截，`SRTP` 触发 `handle_gcmd_srtp()` -> `activate_iommu()`。
- 该路径需要初始化 QI（Queued Invalidation）并分配 `qi->desc`（8KB，order=1）。但当 `CONFIG_PKVM_INTEL_PVIOMMU=y` 时：
  - `divide_memory_pool()` 中为 IOMMU 预留的 `iommu_mem_base` 不会分配（`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/init_finalise.c` 内 `#ifndef CONFIG_PKVM_INTEL_PVIOMMU` 分支）。
  - `pkvm_init_iommu()` 中也不会初始化 `iommu_pool`（`pKVM-IA/arch/x86/kvm/vmx/pkvm/hyp/iommu.c` 内同样的 `#ifndef` 分支）。
  - 但 `initialize_qi()` 仍走 `iommu_zalloc_pages()` 从 `iommu_pool` 分配内存，导致 `hyp_alloc_pages()` 直接 `-ENOMEM`。
- 结果：`activate_iommu()` 失败 -> pKVM 不会置位虚拟 `GSTS.RTPS` -> host 侧一直等不到 `RTPS` -> `IOMMU_WAIT_OP()` 超时后 panic。

**解决方案**

- 方案 1（已验证可启动，推荐先用）：关闭 pvIOMMU，使用 shadow IOMMU 路线  
  - 配置：将 `CONFIG_PKVM_INTEL_PVIOMMU=n` 重新编译安装内核。
- 方案 2（需要代码支持）：保持 pvIOMMU，但补齐“host 动态分配并 donate 给 pKVM”的内存来源  
  - 目标：让 `initialize_qi()` / 相关结构不再依赖 `iommu_pool` 预留内存（或在 pvIOMMU 模式下提供等价的 pool 初始化）。

**验证要点**

- 启动日志不再出现 `handle_gcmd_srtp ... err=-12` / `IOMMU_WAIT_OP timeout` / `DMAR hardware is malfunctioning`。
